# 라우팅

> 한 줄 정의: 라우팅은 URL과 화면 구조를 연결해, 사용자가 어떤 경로에 있을 때 어떤 페이지를 보여줄지 정하는 방식입니다.

## 왜 중요한가

문서 사이트나 관리 화면처럼 콘텐츠 구조가 많은 서비스에서는 URL 체계 자체가 정보 구조의 일부입니다. "페이지 이동되게 해줘" 정도로만 요청하면 경로 규칙, 404 처리, 메뉴 강조, 공유 가능한 URL 같은 핵심이 빠집니다.

즉 라우팅은 단순 이동이 아니라 서비스 구조를 드러내는 장치입니다.

## 언제 쓰는가

- 상세 페이지, 카테고리 목록, 설정 페이지처럼 여러 경로가 있을 때
- 사이드바, 브레드크럼, 검색 결과를 URL과 연결할 때
- 새로고침이나 공유 가능한 링크가 중요한 서비스에서

## 언제 쓰지 말아야 하는가

- 단일 랜딩 페이지 하나만 필요한 경우
- URL 변화 없이 화면 안에서만 짧은 전환이 필요한 경우

<Callout type="info" title="좋은 라우팅은 정보 구조를 그대로 보여줍니다">
URL만 봐도 어떤 카테고리인지, 어떤 상세 화면인지 알 수 있으면 사용자와 개발자 모두 이해하기 쉬워집니다.
</Callout>

## 비개발자가 자주 하는 모호한 요청

- "문서 페이지 라우팅해줘"
- "카테고리별로 열리게 해줘"
- "상세 페이지 이동되게 해줘"

이 요청에는 URL 구조, 없는 경로 처리, 경로와 메뉴의 일관성 같은 조건이 빠져 있습니다.

## 더 좋은 요청으로 바꾸는 방법

- URL 구조를 먼저 적기
- 카테고리와 상세 slug 규칙을 분리하기
- 잘못된 경로와 404 처리도 함께 요청하기
- 내비게이션과 URL이 같은 기준을 따르도록 적기

## 복붙 가능한 프롬프트 예시

### 1. 문서 상세 라우팅

<PromptCodeBlock>
문서 상세 페이지를 /docs/[category]/[slug] 구조로 라우팅해주세요.
존재하지 않는 문서는 404를 보여주고, 사이드바와 브레드크럼도 현재 경로와 같은 구조를 따르게 해주세요.
카테고리별 문서 목록에서 상세 페이지로 자연스럽게 이동하게 해주세요.
</PromptCodeBlock>

### 2. 설정 페이지 라우팅

<PromptCodeBlock>
설정 페이지를 /settings/profile, /settings/security, /settings/notifications 구조로 나눠주세요.
왼쪽 메뉴는 현재 경로를 기준으로 활성 상태가 보이게 하고, 새로고침해도 현재 섹션이 유지되게 해주세요.
</PromptCodeBlock>

### 3. 검색 결과 라우팅

<PromptCodeBlock>
검색 결과 목록에서 항목을 클릭하면 해당 상세 페이지로 이동하게 해주세요.
검색 모달에서 바로 이동한 뒤에도 브레드크럼과 사이드바 active 상태가 현재 경로와 맞게 유지되게 해주세요.
</PromptCodeBlock>

<Callout type="warning" title="URL 구조를 나중에 바꾸면 연결된 탐색 전체가 흔들립니다">
초기에 카테고리, slug, 상세 경로 규칙을 명확히 잡아두는 편이 훨씬 안정적입니다.
</Callout>

## 구현 체크리스트

- URL 구조가 정보 구조를 반영하는가
- 존재하지 않는 경로를 처리하는가
- 메뉴와 브레드크럼이 같은 경로 기준을 따르는가
- 새로고침과 직접 접근에도 같은 페이지가 보이는가
- 검색과 목록에서 상세로 이동할 때 자연스러운가

## 자주 헷갈리는 개념 비교

### 라우팅 vs 동적 라우팅

- 라우팅: 전체 경로 체계를 설계하는 개념
- 동적 라우팅: 경로 일부를 파라미터로 처리하는 방식

### 라우팅 vs 레이아웃

- 라우팅: 어떤 경로가 어떤 페이지를 보여줄지
- 레이아웃: 그 페이지들이 어떤 공통 구조를 공유할지

### 라우팅 vs 정보 구조

- 라우팅: 실제 URL과 페이지 연결 규칙
- 정보 구조: 콘텐츠와 화면의 분류 체계
