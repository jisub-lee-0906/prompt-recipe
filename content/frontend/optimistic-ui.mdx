# 낙관적 UI

> 한 줄 정의: 낙관적 UI는 서버 응답이 오기 전에도 성공할 것이라고 가정하고 화면을 먼저 업데이트하는 방식입니다.

## 왜 중요한가

좋아요, 즐겨찾기, 체크박스 토글처럼 즉시 반응이 중요한 UI에서는 서버 응답을 기다리면 느리게 느껴집니다. 낙관적 UI는 이런 지연을 줄여줍니다. 하지만 실패 복구까지 같이 설계해야 합니다. AI IDE에게 "바로 반영되게 해줘"라고만 하면 실패 처리 없이 끝날 수 있습니다.

## 언제 쓰는가

- 즐겨찾기 추가, 체크 토글, 간단한 상태 변경처럼 성공 확률이 높을 때
- 사용자가 즉시 반응을 기대하는 상호작용에서
- 서버 실패 시 원상복구가 가능한 액션일 때

## 언제 쓰지 말아야 하는가

- 실패 비용이 큰 결제, 삭제, 권한 변경 같은 위험한 작업에서
- 실패 시 원상복구가 복잡하거나 사용자 혼란이 큰 경우
- 데이터 정합성이 특히 중요한 곳에서 무리하게 적용할 때

<Callout type="tip" title="낙관적 UI는 성공만큼 롤백 설계가 중요합니다">
실패했을 때 어떻게 원래 상태로 되돌리고 어떤 메시지를 보여줄지가 함께 있어야 합니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

낙관적 UI를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 액션에 적용할지
- 실패 시 원상복구가 필요한지
- 어떤 피드백을 보여줄지
- 중복 클릭 방지가 필요한지

<PromptCodeBlock>
문서 즐겨찾기 버튼은 낙관적 UI로 처리해주세요.
사용자가 클릭하면 하트 상태가 즉시 바뀌고, 서버 요청이 실패하면 원래 상태로 되돌린 뒤 오류 토스트를 보여주세요.
</PromptCodeBlock>

<PromptCodeBlock>
할 일 완료 체크박스는 낙관적 UI로 동작하게 해주세요.
체크 즉시 스타일이 바뀌고, 서버 실패 시 체크 상태를 되돌린 뒤 인라인 오류를 잠깐 보여주세요.
</PromptCodeBlock>

<PromptCodeBlock>
태그 추가 UI는 낙관적 방식으로 처리해주세요.
태그를 추가하면 목록에 즉시 붙이고, 서버 저장 실패 시 해당 태그를 다시 제거하고 실패 이유를 안내해주세요.
</PromptCodeBlock>

<Callout type="warning" title="위험한 액션에 낙관적 UI를 쓰면 혼란이 커질 수 있습니다">
결제, 삭제, 권한 변경처럼 실패 비용이 큰 작업은 성공 후 확정하는 편이 더 안전할 수 있습니다.
</Callout>

## 구현 체크리스트

- 성공 확률이 높은 액션인가
- 실패 시 원상복구가 가능한가
- 오류 피드백이 있는가
- 중복 클릭이나 중복 요청 방지가 있는가
- 사용자에게 실제 저장 상태가 혼동되지 않는가

## 자주 헷갈리는 개념 비교

### 낙관적 UI vs 로딩 상태

- 낙관적 UI는 먼저 성공처럼 보여줍니다.
- 로딩 상태는 처리 중임을 보여줍니다.

### 낙관적 UI vs 캐시

- 낙관적 UI는 미래 상태를 먼저 보여줍니다.
- 캐시는 이미 받은 데이터를 재사용합니다.

### 낙관적 UI vs 토스트

- 낙관적 UI는 상태 변화를 즉시 반영합니다.
- 토스트는 그 결과를 보조적으로 알려줍니다.
