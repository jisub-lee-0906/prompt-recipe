# 데이터 페칭

> 한 줄 정의: 데이터 페칭은 서버나 API에서 데이터를 읽어와 화면에 보여주는 과정과 방식을 말합니다.

## 왜 중요한가

화면이 예뻐 보여도 실제 데이터가 연결되지 않으면 목업 수준에 머뭅니다. 사용자가 "목록 보여줘"라고 요청할 때, 실제로는 어디서 데이터를 읽는지, 로딩과 실패는 어떻게 처리하는지까지 함께 정해야 실무적인 결과가 나옵니다.

데이터 페칭은 단순 API 연결이 아니라 사용자에게 어떤 상태를 보여줄지까지 포함한 설계입니다.

## 언제 쓰는가

- 문서 목록, 사용자 목록, 검색 결과를 서버에서 가져올 때
- 상세 페이지에서 단일 데이터를 읽어올 때
- 필터나 정렬 변경 시 결과를 다시 받아와야 할 때

## 언제 쓰지 말아야 하는가

- 정적인 콘텐츠만 빌드 시점에 이미 있는 경우
- 외부 데이터 연결 없이 로컬 더미 데이터만 쓰는 경우

<Callout type="info" title="데이터 페칭은 로딩, 성공, 실패를 같이 설계해야 합니다">
API 호출 그 자체보다, 사용자가 그 전후에 무엇을 보게 되는지가 더 중요합니다.
</Callout>

## 비개발자가 자주 하는 모호한 요청

- "API 붙여줘"
- "데이터 불러와서 보여줘"
- "검색 결과 연결해줘"

이 요청에는 언제 불러오는지, 실패하면 어떻게 보일지, 자동 갱신인지 수동 요청인지가 빠져 있습니다.

## 더 좋은 요청으로 바꾸는 방법

- 데이터 소스를 먼저 적기
- 로딩, 에러, 빈 상태를 함께 적기
- 언제 다시 불러오는지 기준을 정하기
- 결과 UI 형태도 같이 적기

## 복붙 가능한 프롬프트 예시

### 1. 목록 데이터 페칭

<PromptCodeBlock>
문서 목록 페이지에서 API로 데이터를 불러와 렌더링해주세요.
로딩 중에는 스켈레톤을 보여주고, 결과가 없으면 빈 상태를, 실패하면 에러 상태와 다시 시도 버튼을 보여주세요.
성공 시에는 카드 목록으로 보여주세요.
</PromptCodeBlock>

### 2. 상세 페이지 데이터 페칭

<PromptCodeBlock>
상세 페이지에서 slug를 기준으로 데이터를 불러와 보여주세요.
데이터를 가져오는 동안 제목과 본문 스켈레톤을 보여주고, 없는 문서면 404 화면으로 보내주세요.
</PromptCodeBlock>

### 3. 필터 변경 재요청

<PromptCodeBlock>
문서 목록 페이지에서 사용자가 필터나 정렬을 바꾸면 데이터를 다시 불러와주세요.
새 요청이 진행 중일 때는 이전 목록을 유지하면서 상단에 로딩 상태를 보여주고, 결과가 오면 목록만 자연스럽게 갱신해주세요.
</PromptCodeBlock>

<Callout type="warning" title="데이터를 불러오는 타이밍이 모호하면 화면이 깜빡이거나 중복 요청이 생길 수 있습니다">
초기 진입, 필터 변경, 검색어 입력처럼 언제 다시 요청해야 하는지 명확히 적는 편이 좋습니다.
</Callout>

## 구현 체크리스트

- 어떤 데이터 소스를 읽는지 정해져 있는가
- 로딩, 에러, 빈 상태가 정의되어 있는가
- 언제 재요청하는지 기준이 있는가
- 성공 시 어떤 UI로 렌더링할지 분명한가
- 요청 중 이전 상태를 유지할지 새 상태로 교체할지 결정되어 있는가

## 자주 헷갈리는 개념 비교

### 데이터 페칭 vs SSG

- 데이터 페칭: 데이터를 읽는 일반 개념
- SSG: 빌드 시점에 미리 읽어 정적으로 생성하는 전략

### 데이터 페칭 vs 상태 관리

- 데이터 페칭: 데이터를 가져오는 과정
- 상태 관리: 가져온 데이터를 어떻게 보관하고 반영하는지

### 데이터 페칭 vs 캐싱

- 데이터 페칭: 데이터를 읽는 행위
- 캐싱: 읽은 결과를 다시 쓰기 위해 보관하는 전략
