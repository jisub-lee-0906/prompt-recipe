# 서버 컴포넌트

> 한 줄 정의: 서버 컴포넌트는 서버에서 실행되고 렌더링되어 클라이언트로 전달되는 컴포넌트 방식입니다.

## 왜 중요한가

Next.js App Router에서는 모든 것을 클라이언트 컴포넌트로 만들 필요가 없습니다. 데이터 읽기나 정적 콘텐츠 렌더링처럼 브라우저 상호작용이 필요 없는 부분은 서버 컴포넌트가 더 자연스럽습니다. AI IDE에게 이 구분을 명시하지 않으면 필요 없는 `use client`가 남발될 수 있습니다.

## 언제 쓰는가

- 파일 시스템, 서버 데이터, 정적 콘텐츠를 읽어 화면을 그릴 때
- 상호작용 없이 마크업과 데이터 조합만 필요한 부분에서
- 번들 크기를 줄이고 싶은 문서 페이지나 목록 영역에서

## 언제 쓰지 말아야 하는가

- 상태, 이벤트, 브라우저 API를 직접 써야 할 때
- `useTheme`, `useState`, `useEffect`, `navigator` 같은 클라이언트 기능이 필요한 경우

<Callout type="tip" title="상호작용이 없으면 먼저 서버 컴포넌트를 검토하는 편이 좋습니다">
특히 문서 데이터 읽기, 사이드바 목록 생성, MDX 파싱 같은 작업은 서버 컴포넌트와 잘 맞습니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

서버 컴포넌트를 요청할 때는 아래를 같이 말해야 합니다.

- 브라우저 상호작용이 필요한지
- 서버에서 미리 읽을 데이터가 있는지
- 클라이언트로 내려보낼 부분이 최소화돼야 하는지
- 하위에 클라이언트 컴포넌트가 섞여도 되는지

</PromptCodeBlock>

<PromptCodeBlock>
문서 상세 페이지 본문 영역은 서버 컴포넌트로 구현해주세요.
서버에서 MDX를 읽고 렌더링하되, 프롬프트 복사 버튼처럼 상호작용이 필요한 부분만 클라이언트 컴포넌트로 분리해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
사이드바는 서버 컴포넌트로 두고, 활성 링크 스타일만 클라이언트에서 처리해주세요.
불필요한 `use client`를 줄여서 번들 크기를 키우지 않게 해주세요.
</PromptCodeBlock>

<Callout type="warning" title="브라우저 기능이 필요한데 서버 컴포넌트로 만들면 바로 막힙니다">
상태, 이벤트, 브라우저 API가 필요한 부분은 클라이언트 컴포넌트로 분리해야 합니다. 서버 컴포넌트는 만능이 아니라 역할이 다른 쪽입니다.
</Callout>

## 구현 체크리스트

- 브라우저 상호작용이 없는가
- 서버에서 읽을 데이터가 있는가
- `use client`가 불필요하게 붙지 않았는가
- 필요한 부분만 클라이언트 하위 컴포넌트로 분리했는가
- 번들 크기와 구조가 더 단순해졌는가

## 자주 헷갈리는 개념 비교

### 서버 컴포넌트 vs 클라이언트 컴포넌트

- 서버 컴포넌트는 서버에서 실행됩니다.
- 클라이언트 컴포넌트는 브라우저에서 상호작용을 담당합니다.

### 서버 컴포넌트 vs SSR

- 서버 컴포넌트는 컴포넌트 단위 개념입니다.
- SSR은 요청 시 HTML을 만드는 렌더링 전략입니다.

### 서버 컴포넌트 vs SSG

- 서버 컴포넌트는 구성 방식입니다.
- SSG는 페이지를 빌드 시점에 만드는 전략입니다.
