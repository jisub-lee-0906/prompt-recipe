# 프론트엔드 캐시

> 한 줄 정의: 프론트엔드 캐시는 이미 가져온 데이터를 브라우저 쪽에서 재사용해 불필요한 재요청과 화면 흔들림을 줄이는 전략입니다.

## 왜 중요한가

목록 페이지를 왔다가 다시 돌아왔을 때 매번 처음부터 로딩하면 사용자는 답답함을 느낍니다. 프론트엔드 캐시는 같은 데이터를 다시 쓸 수 있게 해 이런 경험을 개선합니다. AI IDE에게 "빠르게 해줘"라고 하기보다 캐시 전략을 요청해야 구현 방향이 명확해집니다.

## 언제 쓰는가

- 목록과 상세를 오가며 같은 데이터를 자주 다시 볼 때
- 검색 결과나 필터 결과를 잠시 유지하고 싶을 때
- 불필요한 네트워크 요청과 깜빡임을 줄이고 싶을 때

## 언제 쓰지 말아야 하는가

- 데이터가 매우 민감하고 항상 최신값이어야 할 때
- 캐시 유지가 오히려 잘못된 오래된 정보 노출로 이어질 때
- 정적 콘텐츠만 다루고 별도 클라이언트 캐시가 필요 없을 때

<Callout type="tip" title="캐시는 속도뿐 아니라 화면 안정성에도 영향을 줍니다">
이전 데이터가 남아 있으면 로딩 중에도 화면이 덜 흔들리고, 사용자는 더 빠르게 느낍니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

프론트엔드 캐시를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 데이터를 다시 사용해야 하는지
- 얼마나 최신성을 유지해야 하는지
- 뒤로 가기나 재방문 시 어떤 경험을 원하는지
- 캐시와 재검증을 어떻게 조합할지

<PromptCodeBlock>
문서 목록 데이터를 프론트엔드 캐시로 유지해주세요.
사용자가 상세 페이지를 보고 뒤로 돌아왔을 때 이전 목록과 스크롤 위치가 최대한 유지되고, 필요할 때만 백그라운드에서 새 데이터를 다시 불러오게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
검색 결과는 입력이 바뀌지 않는 한 잠시 캐시해두고, 같은 검색어로 다시 들어오면 즉시 보여주세요.
대신 일정 시간이 지나면 백그라운드에서 다시 확인해 최신 결과로 갱신해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
사용자 상세 데이터를 상세 페이지와 권한 변경 모달에서 함께 써야 합니다.
같은 사용자 데이터를 여러 번 요청하지 않도록 프론트엔드 캐시를 활용하고, 변경 후에는 관련 캐시를 적절히 갱신해주세요.
</PromptCodeBlock>

<Callout type="warning" title="캐시를 쓰면 오래된 데이터 처리 기준도 같이 있어야 합니다">
캐시 자체보다 더 중요한 건 언제 다시 불러올지, 언제 무효화할지입니다. 그 기준이 없으면 잘못된 정보가 오래 남을 수 있습니다.
</Callout>

## 구현 체크리스트

- 어떤 데이터를 캐시할지 명확한가
- 언제 다시 검증할지 기준이 있는가
- 뒤로 가기나 재방문 경험이 좋아지는가
- 수정 후 캐시 무효화가 필요한가
- 최신성 요구와 성능 요구가 균형 잡혀 있는가

## 자주 헷갈리는 개념 비교

### 프론트엔드 캐시 vs 백엔드 캐시

- 프론트엔드 캐시는 브라우저 쪽 재사용 전략입니다.
- 백엔드 캐시는 서버 응답 자체를 빠르게 만드는 전략입니다.

### 프론트엔드 캐시 vs SSG

- 프론트엔드 캐시는 클라이언트 측 데이터 재사용 전략입니다.
- SSG는 페이지를 빌드 시점에 생성하는 렌더링 전략입니다.

### 프론트엔드 캐시 vs 낙관적 UI

- 캐시는 이미 받은 데이터를 재사용합니다.
- 낙관적 UI는 아직 서버 응답이 오기 전 성공을 가정하고 먼저 화면을 바꿉니다.
