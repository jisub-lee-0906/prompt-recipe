# SSR

> 한 줄 정의: SSR은 사용자의 요청이 들어올 때마다 서버에서 HTML을 생성해 응답하는 렌더링 방식입니다.

## 왜 중요한가

정적 생성이 잘 맞지 않는 화면도 있습니다. 사용자별 데이터가 필요하거나 요청마다 내용이 달라진다면 SSR이 더 자연스럽습니다. AI IDE에게 "서버에서 렌더링해줘"보다 SSR이라고 명시해야 SSG, CSR과의 차이를 기준으로 더 올바른 선택을 할 수 있습니다.

## 언제 쓰는가

- 요청마다 사용자별 내용이 달라질 때
- 로그인 상태, 권한, 실시간성 있는 데이터에 따라 화면이 바뀔 때
- 초기 HTML을 서버에서 안정적으로 만들어야 할 때

## 언제 쓰지 말아야 하는가

- 빌드 시 미리 만들어도 충분한 정적 문서 페이지일 때
- 실시간성은 낮고 캐시 이점이 더 중요한 화면일 때
- 브라우저에서만 처리해도 충분한 순수 상호작용 화면일 때

<Callout type="tip" title="SSR은 요청마다 달라지는 화면에서 강합니다">
사용자별 대시보드, 권한에 따라 달라지는 관리자 화면처럼 요청 시점 정보가 중요한 경우에 더 적합합니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

SSR을 요청할 때는 아래를 같이 말해야 합니다.

- 왜 빌드 시점 생성이 아닌 요청 시점 렌더링이 필요한지
- 어떤 사용자별 데이터가 필요한지
- 비로그인이나 권한 부족 처리를 어떻게 할지
- 초기 HTML에 무엇이 포함돼야 하는지

<PromptCodeBlock>
로그인 사용자별 대시보드는 요청 시점에 서버에서 렌더링해주세요.
세션과 권한을 확인한 뒤 사용자별 데이터를 포함한 HTML을 응답하게 하고, 비로그인 상태면 로그인 페이지로 보내주세요.
</PromptCodeBlock>

<PromptCodeBlock>
관리자 통계 화면은 SSR로 렌더링해주세요.
요청 시점에 최신 통계 데이터를 읽어와 초기 HTML에 포함하고, 접근 권한이 없으면 403 성격의 안내 화면을 보여주세요.
</PromptCodeBlock>

<PromptCodeBlock>
문서 사이트 홈에서 개인화 추천 영역만 SSR로 처리해주세요.
로그인 사용자는 최근 본 문서를 기준으로 추천을 받고, 비로그인 사용자는 기본 추천 문서를 보게 해주세요.
</PromptCodeBlock>

<Callout type="warning" title="모든 페이지를 SSR로 돌리면 운영과 캐시 전략이 복잡해질 수 있습니다">
SSR은 유연하지만 요청마다 서버 작업이 필요합니다. 정적으로 가능한 화면까지 무조건 SSR로 돌리는 것은 효율적이지 않을 수 있습니다.
</Callout>

## 구현 체크리스트

- 요청 시점 렌더링이 필요한 이유가 분명한가
- 사용자별 데이터와 권한 처리 기준이 있는가
- 비로그인, 권한 부족 상태가 정의되어 있는가
- 초기 HTML에 꼭 필요한 내용이 포함되는가
- SSG나 CSR보다 SSR이 더 적절한가

## 자주 헷갈리는 개념 비교

### SSR vs SSG

- SSR은 요청 시점에 HTML을 만듭니다.
- SSG는 빌드 시점에 HTML을 만듭니다.

### SSR vs CSR

- SSR은 서버가 초기 HTML을 만듭니다.
- CSR은 브라우저가 화면을 조립합니다.

### SSR vs 서버 컴포넌트

- SSR은 페이지 렌더링 시점 전략입니다.
- 서버 컴포넌트는 컴포넌트 구성 방식입니다.
