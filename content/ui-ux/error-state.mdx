# 에러 상태

> 한 줄 정의: 에러 상태는 실패 사실만 보여주는 화면이 아니라, 무엇이 잘못됐고 사용자가 다음에 무엇을 할 수 있는지 설명하는 UI입니다.

## 왜 중요한가

에러가 났을 때 화면이 멈추거나 개발자용 문구만 보이면 사용자는 서비스 전체를 불안하게 느낍니다. AI IDE에게 에러 상태를 정확히 요청하면 단순 경고 문구가 아니라 재시도, 이전 화면 복귀, 권한 안내처럼 복구 가능한 경험으로 바꿀 수 있습니다.

## 언제 쓰는가

- 데이터 요청이 실패했을 때
- 권한 부족으로 접근이 막혔을 때
- 삭제, 저장, 업로드 같은 작업이 정상적으로 끝나지 않았을 때

## 언제 쓰지 말아야 하는가

- 단순히 결과가 없는 정상 상태를 실패처럼 보이게 만들면 안 될 때
- 로딩 중인데 실패처럼 오해될 수 있을 때
- 사용자에게 보여줄 필요 없는 내부 기술 오류를 그대로 노출하면 안 될 때

<Callout type="warning" title="에러 상태는 사용자를 탓하면 안 됩니다">
`잘못된 요청입니다`처럼 책임을 사용자에게 돌리는 문구는 경험을 나쁘게 만듭니다. 무엇이 막혔는지 설명하고, 가능한 다음 행동을 제시하는 쪽이 훨씬 낫습니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

에러 상태를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 종류의 실패인지
- 사용자가 즉시 할 수 있는 복구 행동이 있는지
- 일시적 실패인지, 권한 부족인지, 영구적 차단인지
- 기술적인 상세 정보는 어디까지 보여줄지

<PromptCodeBlock>
문서 데이터를 불러오지 못했을 때 보여줄 에러 상태 UI를 만들어주세요.
문제를 짧게 설명하고, `다시 시도` 버튼과 이전 화면으로 돌아갈 수 있는 보조 액션을 함께 넣어주세요.
네트워크 문제와 권한 문제는 문구를 다르게 보여주세요.
</PromptCodeBlock>

<PromptCodeBlock>
폼 제출이 실패했을 때의 에러 상태를 설계해주세요.
상단에는 전체 실패 이유를 짧게 안내하고, 입력값 자체가 잘못된 경우에는 해당 필드 근처에 인라인 오류도 함께 보여주세요.
서버 장애처럼 사용자가 고칠 수 없는 경우에는 연락 방법이나 잠시 후 재시도 안내를 넣어주세요.
</PromptCodeBlock>

<PromptCodeBlock>
권한이 없는 페이지에 접근했을 때의 에러 상태를 만들어주세요.
단순히 `접근 불가`라고 끝내지 말고, 왜 접근할 수 없는지와 어디로 돌아가야 하는지 함께 보여주세요.
관리자에게 권한 요청이 필요한 서비스라면 요청 방법까지 안내해주세요.
</PromptCodeBlock>

<Callout type="tip" title="에러 유형을 나누면 UX가 훨씬 명확해집니다">
네트워크 실패, 권한 부족, 삭제된 리소스는 모두 다른 상태입니다. 같은 빨간 박스 하나로 처리하면 사용자는 무엇을 해야 하는지 알기 어렵습니다.
</Callout>

## 구현 체크리스트

- 실패 원인이 사용자 관점에서 이해 가능한가
- 다시 시도나 복귀 같은 다음 행동이 있는가
- 빈 상태와 시각적으로 구분되는가
- 사용자 잘못이 아닌 경우 책임을 떠넘기는 문구가 없는가
- 권한 문제와 일시적 오류를 구분하는가

## 자주 헷갈리는 개념 비교

### 에러 상태 vs 빈 상태

- 에러 상태는 문제가 발생한 비정상 상황입니다.
- 빈 상태는 결과가 없는 정상 상황입니다.

### 에러 상태 vs 토스트

- 에러 상태는 화면의 주요 콘텐츠를 대체할 정도로 중요한 실패 표현입니다.
- 토스트는 짧게 알리고 지나가는 보조 피드백에 가깝습니다.

### 에러 상태 vs 폼 검증 오류

- 에러 상태는 페이지 또는 작업 전체 수준의 실패를 다룹니다.
- 폼 검증 오류는 특정 입력 필드 수준의 문제를 다룹니다.
