# 디자인 토큰

> 한 줄 정의: 디자인 토큰은 색상, 간격, 폰트 크기 같은 디자인 값을 재사용 가능한 단위로 정의한 규칙입니다.

## 왜 중요한가

디자인 시스템이 전체 체계라면, 디자인 토큰은 그 체계를 움직이는 가장 작은 값입니다. 토큰이 없으면 화면마다 비슷한 색과 간격이 조금씩 달라지기 쉽습니다. AI IDE에게도 "간격 통일해줘"보다 토큰 기준을 정의하라고 요청하는 편이 훨씬 안정적입니다.

## 언제 쓰는가

- 다크/라이트 모드에서 같은 의미의 색을 다르게 매핑해야 할 때
- 간격, 반경, 그림자, 타이포 크기를 일관되게 관리하고 싶을 때
- 여러 컴포넌트가 공통 기준을 따라야 할 때

## 언제 쓰지 말아야 하는가

- 일회성 실험 화면 하나만 빠르게 만들 때
- 공통 규칙보다 즉흥 수정이 더 많은 초기 스케치 단계일 때

<Callout type="tip" title="토큰은 이름이 의미 중심이어야 합니다">
`blue-500`보다 `primary`, `muted`, `danger`처럼 역할 중심 이름이 나중에 유지보수하기 더 좋습니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

디자인 토큰을 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 값들을 토큰화할지
- 의미 기반 이름을 쓸지
- 다크/라이트 모드를 함께 지원할지
- CSS 변수나 테마 시스템과 연결할지

<PromptCodeBlock>
문서 사이트 전반에 사용할 디자인 토큰을 정의해주세요.
색상은 `background`, `foreground`, `primary`, `muted`, `danger` 기준으로 나누고, spacing과 radius도 공통 토큰으로 정리해주세요.
라이트/다크 모드 모두 대응되게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
버튼, 카드, 입력 필드에서 공통으로 쓰는 spacing 토큰을 정리해주세요.
`space-2`, `space-4`, `space-6`처럼 단계형으로 만들고, 컴포넌트별 임의 픽셀 값 사용을 줄일 수 있게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
다크 모드와 라이트 모드에서 같은 의미를 유지하는 색상 토큰 체계를 만들어주세요.
배경, 경계선, 강조색, 위험색이 모드마다 바뀌더라도 역할 이름은 유지되게 해주세요.
</PromptCodeBlock>

<Callout type="warning" title="값 중심 이름은 나중에 의미가 바뀌면 바로 흔들립니다">
`gray-200` 같은 이름은 현재 값에는 맞아도 역할 변경에 약합니다. 의미 중심 이름이 더 오래 갑니다.
</Callout>

## 구현 체크리스트

- 색상, 간격, 반경 등 공통 값이 토큰화되었는가
- 이름이 의미 중심인가
- 다크/라이트 모드 대응이 되는가
- 디자인 시스템과 연결되는가
- 임의 값 사용을 줄일 수 있는가

## 자주 헷갈리는 개념 비교

### 디자인 토큰 vs 디자인 시스템

- 디자인 토큰은 가장 작은 값 단위입니다.
- 디자인 시스템은 그 값을 포함한 전체 운영 체계입니다.

### 디자인 토큰 vs CSS 변수

- 디자인 토큰은 개념과 이름 체계입니다.
- CSS 변수는 그것을 구현하는 한 방식입니다.

### 디자인 토큰 vs 테마

- 디자인 토큰은 공통 의미 단위입니다.
- 테마는 그 토큰 값을 모드나 브랜드에 맞게 매핑한 결과일 수 있습니다.
