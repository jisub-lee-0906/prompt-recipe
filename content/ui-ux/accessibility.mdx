# 접근성

> 한 줄 정의: 접근성은 다양한 입력 방식과 신체 조건, 환경 차이를 가진 사용자가 제품을 사용할 수 있게 만드는 기준입니다.

## 왜 중요한가

접근성은 일부 사용자만을 위한 옵션이 아니라 제품 품질의 기본값입니다. 키보드만으로도 사용할 수 있어야 하고, 제목 구조가 논리적이어야 하며, 상태 변화가 색상에만 의존하지 않아야 합니다. AI IDE에게 접근성을 명시하지 않으면 "보이는 화면"은 만들어도 실제 사용 가능한 화면이 빠지기 쉽습니다.

## 언제 쓰는가

- 사실상 모든 화면과 컴포넌트에서 기본 기준으로 적용해야 할 때
- 모달, 폼, 메뉴, 검색 모달처럼 상호작용이 많은 UI를 만들 때
- 문서 사이트처럼 제목 구조와 탐색 체계가 중요한 서비스일 때

## 언제 쓰지 말아야 하는가

- 예외가 없습니다. 접근성은 특정 화면에서만 고려하는 추가 옵션이 아니라 기본 요구사항입니다.

<Callout type="tip" title="접근성은 전체 사용자 경험을 더 안정적으로 만듭니다">
명확한 제목 구조, 좋은 대비, 키보드 탐색, 상태 전달은 보조 기술 사용자뿐 아니라 대부분의 사용자에게도 더 좋은 경험을 만듭니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

접근성을 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 화면이나 컴포넌트가 우선 대상인지
- 키보드 탐색이 필요한지
- 제목 구조와 상태 전달이 중요한지
- 스크린리더, 포커스 이동, 색상 대비 중 무엇을 구체적으로 챙겨야 하는지

<PromptCodeBlock>
문서 사이트 전반에 접근성 기준을 적용해주세요.
헤더, 사이드바, 검색 모달, 문서 본문, TOC가 키보드만으로 탐색 가능해야 하고, 제목 구조와 현재 위치 표시가 스크린리더에도 전달되게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
모달 컴포넌트를 접근성 기준에 맞게 구현해주세요.
열리면 포커스가 모달 안으로 이동하고, 닫히면 원래 버튼으로 돌아가야 합니다.
제목과 설명이 스크린리더에 전달되어야 하고, ESC로 닫을 수 있어야 합니다.
</PromptCodeBlock>

<PromptCodeBlock>
회원가입 폼의 접근성을 강화해주세요.
각 입력 필드는 라벨과 연결되어야 하고, 오류 메시지는 어떤 필드의 문제인지 명확히 전달되어야 합니다.
키보드만으로 입력과 제출이 가능해야 하고, 색상만으로 오류를 표현하지 말아주세요.
</PromptCodeBlock>

<Callout type="warning" title="색상 대비만 맞춘다고 접근성이 끝나지 않습니다">
포커스 이동, 제목 구조, 라벨 연결, 상태 전달까지 모두 포함해야 실제로 접근 가능한 UI가 됩니다.
</Callout>

## 구현 체크리스트

- 키보드만으로 사용 가능한가
- 포커스 상태가 항상 보이는가
- 라벨과 입력이 연결되어 있는가
- 제목 구조가 논리적인가
- 상태 변화가 색상 외의 방식으로도 전달되는가

## 자주 헷갈리는 개념 비교

### 접근성 vs 프론트엔드 접근성

- 접근성은 제품 설계와 콘텐츠 기준까지 포함한 넓은 개념입니다.
- 프론트엔드 접근성은 그 기준을 코드로 구현하는 관점입니다.

### 접근성 vs 반응형 설계

- 접근성은 누구나 사용할 수 있게 만드는 기준입니다.
- 반응형 설계는 화면 크기에 맞게 배치가 바뀌는 기준입니다.

### 접근성 vs 사용성

- 접근성은 사용 가능성의 최소 기준에 가깝습니다.
- 사용성은 그 위에서 얼마나 쉽고 자연스러운지도 포함합니다.
