# 디자인 시스템

> 한 줄 정의: 디자인 시스템은 반복되는 UI와 사용 규칙을 하나의 체계로 묶어 제품 전반의 일관성을 유지하는 방식입니다.

## 왜 중요한가

화면을 하나씩 빠르게 만들다 보면 버튼 크기, 카드 간격, 입력 필드 스타일, 상태 색상이 조금씩 달라지기 쉽습니다. 디자인 시스템이 없으면 AI IDE도 매번 새로운 화면을 만들 때마다 다른 기준을 적용하게 됩니다. 반대로 디자인 시스템을 먼저 정의하면 "같은 규칙을 따르는 화면"을 지속적으로 만들 수 있습니다.

## 언제 쓰는가

- 문서 사이트, 관리자, 서비스 대시보드처럼 화면 수가 계속 늘어날 때
- 같은 버튼, 카드, 배지, 입력 필드를 여러 화면에서 반복 사용할 때
- 팀이 여러 명이거나 이후 유지보수가 길게 이어질 때

## 언제 쓰지 말아야 하는가

- 일회성 프로토타입 하나만 짧게 만들고 끝낼 때
- 아직 제품 방향이 너무 유동적이라 공통 규칙 자체가 자주 바뀌는 초기 실험 단계일 때

<Callout type="tip" title="디자인 시스템은 예쁘게 보이기 위한 장식이 아닙니다">
핵심은 일관성과 재사용성입니다. 버튼과 카드의 모양만 모아두는 것이 아니라, 언제 어떤 variant를 써야 하는지까지 정해야 실제로 시스템처럼 작동합니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

디자인 시스템을 요청할 때는 아래를 같이 말해야 합니다.

- 공통으로 관리할 컴포넌트가 무엇인지
- 상태별 규칙이 필요한지
- 라이트/다크 모드나 관리자/사용자 화면 같은 범위 차이가 있는지
- variant와 사용 기준을 같이 정리할지

<PromptCodeBlock>
문서 사이트 전반에 적용할 디자인 시스템 기준을 정리해주세요.
버튼, 카드, 배지, 입력 필드, 사이드바 링크, 코드 블록의 공통 스타일과 상태별 규칙을 정의하고, 라이트/다크 모드에서도 같은 위계가 유지되게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
관리자 화면용 디자인 시스템 초안을 만들어주세요.
테이블, 필터 바, 모달, 토스트, 상태 배지, 폼 필드의 기본 스타일과 variant를 정리하고, 성공/경고/오류 상태 색상 규칙도 함께 정의해주세요.
컴포넌트 이름과 사용 기준까지 같이 문서화해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
프로젝트에서 반복되는 UI를 디자인 시스템 관점으로 재정리해주세요.
우선순위는 버튼, 입력 필드, 카드, 배지, 탭 순서로 두고, 각 컴포넌트에 대해 언제 기본형을 쓰고 언제 강조형을 쓰는지 설명해주세요.
임의 스타일을 화면마다 새로 만들지 않게 가이드 중심으로 정리해주세요.
</PromptCodeBlock>

<Callout type="warning" title="컴포넌트 목록만 있다고 디자인 시스템이 되지는 않습니다">
핵심은 사용 규칙입니다. 같은 버튼이라도 언제 `기본`, `보조`, `위험` variant를 써야 하는지까지 있어야 실제로 일관성이 유지됩니다.
</Callout>

## 구현 체크리스트

- 공통 컴포넌트 목록이 정리되어 있는가
- 상태별 스타일 규칙이 있는가
- 라이트/다크 모드 기준이 함께 정리되어 있는가
- variant와 사용 기준이 연결되어 있는가
- 임의 스타일을 막을 수 있을 정도로 구체적인가

## 자주 헷갈리는 개념 비교

### 디자인 시스템 vs 컴포넌트 라이브러리

- 디자인 시스템은 규칙과 사용 기준까지 포함한 체계입니다.
- 컴포넌트 라이브러리는 재사용 가능한 UI 묶음에 가깝습니다.

### 디자인 시스템 vs 디자인 토큰

- 디자인 시스템은 전체 운영 체계입니다.
- 디자인 토큰은 색상, 간격, 폰트 같은 가장 작은 단위입니다.

### 디자인 시스템 vs 레이아웃

- 디자인 시스템은 제품 전반의 공통 기준입니다.
- 레이아웃은 개별 화면의 구조 패턴입니다.
