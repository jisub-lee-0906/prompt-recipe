# 수용 기준

> 한 줄 정의: 수용 기준은 기능이 완료되었는지 테스트 가능한 문장으로 판단할 수 있게 만든 기준입니다.

## 왜 중요한가

성공 기준이 방향을 잡아준다면, 수용 기준은 실제 검수와 테스트를 가능하게 합니다. AI IDE에게 요청할 때 수용 기준까지 함께 적으면 결과를 더 객관적으로 확인할 수 있고, "대충 비슷하게 된 것"과 "실제로 완료된 것"을 구분할 수 있습니다.

## 언제 쓰는가

- 기능 구현 전에 완료 조건을 테스트 가능한 문장으로 정리할 때
- 개발과 QA가 같은 기준으로 결과를 확인해야 할 때
- 반복 수정이 많은 작업에서 검수 기준을 고정하고 싶을 때

## 언제 쓰지 말아야 하는가

- 예외가 거의 없습니다. 기능 단위 작업이라면 최소한의 수용 기준이 있는 편이 좋습니다.

<Callout type="tip" title="수용 기준은 확인 가능한 문장이어야 합니다">
`깔끔하다`, `좋다` 같은 표현은 수용 기준이 아닙니다. `버튼을 누르면 모달이 열린다`처럼 확인 가능한 문장이어야 합니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

수용 기준을 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 행동을 확인해야 하는지
- 어떤 상태까지 포함할지
- 성공뿐 아니라 실패나 빈 상태도 포함할지
- 플랫폼 차이가 있는지

<PromptCodeBlock>
문서 검색 기능의 수용 기준을 테스트 가능한 문장으로 정리해주세요.
사용자가 Cmd/Ctrl+K로 검색창을 열 수 있어야 하고, 제목·설명·태그 기준으로 결과가 필터링되어야 하며, 결과 클릭 시 해당 문서로 이동해야 합니다.
검색 결과가 없을 때는 빈 상태를 보여줘야 합니다.
</PromptCodeBlock>

<PromptCodeBlock>
문서 상세 페이지의 수용 기준을 작성해주세요.
데스크톱에서는 사이드바, 본문, TOC가 보여야 하고 모바일에서는 본문 중심 구조여야 합니다.
프롬프트 복사 버튼과 테마 전환도 정상 동작해야 합니다.
</PromptCodeBlock>

<PromptCodeBlock>
회원가입 폼의 수용 기준을 정리해주세요.
필수 입력 오류가 필드별로 보여야 하고, 제출 중에는 버튼이 비활성화되어야 하며, 성공 시 다음 화면으로 이동해야 합니다.
오류가 있으면 입력값은 유지되어야 합니다.
</PromptCodeBlock>

<Callout type="warning" title="수용 기준은 너무 넓어도 문제입니다">
한 문장에 여러 조건을 과하게 넣으면 무엇이 실패했는지 확인하기 어려워집니다. 한 기준은 한 행동이나 한 결과에 가깝게 쪼개는 편이 좋습니다.
</Callout>

## 구현 체크리스트

- 각 기준이 테스트 가능한 문장인가
- 성공과 예외 상태가 포함되는가
- 확인 주체가 사용자 관점에서 이해 가능한가
- 기능 범위와 정확히 맞는가
- 지나치게 추상적인 표현이 없는가

## 자주 헷갈리는 개념 비교

### 수용 기준 vs 성공 기준

- 수용 기준은 테스트 가능한 문장으로 더 구체화된 기준입니다.
- 성공 기준은 더 넓은 완료 판단 기준입니다.

### 수용 기준 vs 체크리스트

- 수용 기준은 완료 조건 문장입니다.
- 체크리스트는 작업 중 확인할 항목 목록입니다.

### 수용 기준 vs QA 테스트 케이스

- 수용 기준은 무엇을 만족해야 하는지에 집중합니다.
- QA 테스트 케이스는 어떻게 검증할지 절차까지 포함할 수 있습니다.
