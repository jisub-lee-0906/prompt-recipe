# 엣지 케이스

> 한 줄 정의: 엣지 케이스는 정상 흐름에서는 드물지만 실제 서비스에서 반드시 고려해야 하는 예외 상황입니다.

## 왜 중요한가

정상 흐름만 구현하면 데모는 그럴듯해 보여도 실제 운영에서는 쉽게 무너집니다. 검색 결과가 없을 수도 있고, 세션이 만료될 수도 있고, 잘못된 URL로 들어올 수도 있습니다. AI IDE에게도 예외 상황을 같이 적어줘야 실전형 결과가 나옵니다.

## 언제 쓰는가

- 검색, 로그인, 결제, 폼 제출처럼 실패 가능성이 있는 기능을 설계할 때
- QA 전에 예외 상황을 미리 정리하고 싶을 때
- "정상 흐름은 되는데 실제 사용에서 자주 깨지는 문제"를 줄이고 싶을 때

## 언제 쓰지 말아야 하는가

- 사실상 모든 주요 기능에서 기본적으로 고려해야 합니다. 별도 문서가 없더라도 설계 단계에서 함께 적는 편이 낫습니다.

<Callout type="tip" title="엣지 케이스를 먼저 적으면 결과물이 훨씬 실전적이 됩니다">
정상 동작만 설명하는 요청보다 빈 데이터, 만료, 잘못된 경로, 네트워크 오류까지 적은 요청이 훨씬 강합니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

엣지 케이스를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 종류의 예외를 중요하게 볼지
- 각 예외에서 사용자에게 무엇을 보여줄지
- 복구 경로가 있는지
- 빌드나 라우팅 수준에서 막아야 하는 경우가 있는지

<PromptCodeBlock>
검색 기능의 엣지 케이스를 함께 처리해주세요.
결과가 없을 때는 빈 상태를 보여주고, 네트워크 오류가 나면 다시 시도 버튼을 보여주세요.
너무 짧은 검색어는 안내 메시지로 막고, 잘못된 URL 쿼리는 기본값으로 복구해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
로그인 흐름의 엣지 케이스를 정리해주세요.
비밀번호 오류, 계정 잠금, 세션 만료, 네트워크 실패, 이미 로그인된 사용자가 로그인 페이지에 들어온 경우를 각각 어떻게 처리할지 포함해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
문서 페이지에서 발생할 수 있는 엣지 케이스를 처리해주세요.
존재하지 않는 slug는 404로 보내고, frontmatter가 잘못된 문서는 빌드 단계에서 실패하게 해주세요.
헤딩이 없는 문서는 TOC를 비우고 레이아웃이 깨지지 않게 해주세요.
</PromptCodeBlock>

<Callout type="warning" title="엣지 케이스는 마지막에 몰아서 붙이면 대개 급하게 새게 됩니다">
정상 흐름이 완성된 뒤에 뒤늦게 붙이면 구조를 다시 고쳐야 하는 경우가 많습니다. 설계 초반부터 함께 적는 편이 훨씬 효율적입니다.
</Callout>

## 구현 체크리스트

- 빈 상태가 고려되어 있는가
- 오류와 권한 문제를 구분하는가
- 잘못된 입력과 잘못된 경로가 처리되는가
- 사용자에게 다음 행동이 제시되는가
- 빌드 단계와 런타임 단계 예외가 구분되는가

## 자주 헷갈리는 개념 비교

### 엣지 케이스 vs 실패 시나리오

- 엣지 케이스는 예외 상황 전반을 다룹니다.
- 실패 시나리오는 그중 실패 흐름을 더 구체적으로 다룹니다.

### 엣지 케이스 vs 성공 기준

- 엣지 케이스는 무엇이 깨질 수 있는지 봅니다.
- 성공 기준은 무엇이 충족되면 완료인지 봅니다.

### 엣지 케이스 vs 에러 상태

- 엣지 케이스는 설계 대상입니다.
- 에러 상태는 그 결과 화면 중 하나입니다.
