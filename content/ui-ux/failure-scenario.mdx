# 실패 시나리오

> 한 줄 정의: 실패 시나리오는 기능이 예상대로 완료되지 않았을 때 사용자가 무엇을 보고 무엇을 할 수 있어야 하는지 정리한 흐름입니다.

## 왜 중요한가

엣지 케이스가 예외 목록이라면, 실패 시나리오는 그중 실패 흐름을 사용자 경험 관점에서 풀어낸 문서입니다. AI IDE에게 "실패 처리도 해줘"보다 어떤 상황에서 어떤 메시지와 복구 경로가 필요한지 시나리오로 적어줘야 실제 화면과 문구가 더 좋아집니다.

## 언제 쓰는가

- 로그인 실패, 결제 실패, 업로드 실패처럼 복구 흐름이 중요한 기능에서
- 에러 상태와 토스트, 다시 시도 경로를 함께 설계해야 할 때
- QA 전에 실패 경험을 구체적으로 점검하고 싶을 때

## 언제 쓰지 말아야 하는가

- 사실상 주요 기능에서는 대부분 함께 고려하는 편이 낫습니다. 별도 문서가 없더라도 설계 단계에서 같이 적는 게 좋습니다.

<Callout type="tip" title="실패 시나리오는 메시지보다 복구 경로가 핵심입니다">
무엇이 실패했는지도 중요하지만, 사용자가 다음에 무엇을 할 수 있는지가 더 중요합니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

실패 시나리오를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 실패 유형을 구분할지
- 각 실패에서 사용자에게 무엇을 보여줄지
- 다시 시도, 이전 단계 이동, 문의 같은 복구 경로가 있는지
- 토스트, 인라인 오류, 전체 에러 상태 중 무엇이 적절한지

<PromptCodeBlock>
로그인 실패 시나리오를 설계해주세요.
비밀번호 오류, 계정 잠금, 세션 만료, 네트워크 실패를 구분하고, 각 경우에 사용자에게 보여줄 메시지와 다음 행동 경로를 함께 정리해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
결제 실패 시나리오를 정리해주세요.
결제 승인 실패, 중복 결제 방지, 네트워크 오류, 카드 한도 초과를 구분하고, 각 상황에서 다시 시도할지 다른 결제 수단으로 넘어갈지 결정할 수 있게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
문서 저장 실패 시나리오를 설계해주세요.
임시 저장 실패와 최종 발행 실패를 구분하고, 사용자가 입력한 내용은 최대한 유지되게 하며, 다시 시도 버튼과 오류 로그 확인 경로를 적절히 안내해주세요.
</PromptCodeBlock>

<Callout type="warning" title="실패 시나리오를 에러 문구 한 줄로 끝내면 실제 복구가 막힙니다">
실패 원인에 따라 사용자가 해야 할 다음 행동이 달라집니다. 모든 실패를 같은 빨간 박스로만 처리하면 UX가 급격히 약해집니다.
</Callout>

## 구현 체크리스트

- 실패 유형이 구분되는가
- 각 실패에 맞는 메시지와 액션이 있는가
- 다시 시도와 다른 대안 경로가 정의되어 있는가
- 사용자 입력이나 진행 상태를 최대한 유지하는가
- 에러 상태와 토스트, 인라인 오류 역할이 구분되는가

## 자주 헷갈리는 개념 비교

### 실패 시나리오 vs 엣지 케이스

- 실패 시나리오는 실패 흐름 자체를 구체적으로 다룹니다.
- 엣지 케이스는 더 넓은 예외 상황 목록입니다.

### 실패 시나리오 vs 에러 상태

- 실패 시나리오는 흐름 전체입니다.
- 에러 상태는 그 흐름 중 한 화면 표현입니다.

### 실패 시나리오 vs 폴백

- 실패 시나리오는 실패 경험 전체를 설계합니다.
- 폴백은 그중 대체 경로 한 가지에 가깝습니다.
