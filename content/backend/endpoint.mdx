# 엔드포인트

> 한 줄 정의: 엔드포인트는 API에서 특정 기능을 수행하기 위해 요청을 보내는 개별 경로와 진입 지점입니다.

## 왜 중요한가

기획자가 "문서 API 하나 만들어주세요"라고 말하면 실제로는 목록 조회, 상세 조회, 생성, 수정, 삭제처럼 여러 요청 단위가 필요합니다. 엔드포인트라는 개념을 정확히 쓰면 AI IDE가 기능을 더 잘 분리하고, 프론트엔드도 어떤 화면에서 어떤 요청을 쓰는지 명확하게 연결할 수 있습니다.

## 언제 쓰는가

- 목록 조회, 상세 조회, 생성, 수정, 삭제를 분리해야 할 때
- 프론트엔드 화면과 백엔드 요청 경로를 맞춰야 할 때
- API 문서와 테스트 기준을 정리해야 할 때

## 언제 쓰지 말아야 하는가

- 사실상 모든 API 설계에서 필요한 기본 개념이라 "안 쓰는 상황"보다는 "모호하게 쓰는 상황"을 피해야 합니다

<Callout type="info" title="엔드포인트는 기능 단위로 나눠야 합니다">
하나의 거대한 엔드포인트에 모든 동작을 몰아넣으면 프론트엔드 연결도 어렵고 유지보수도 나빠집니다. 조회, 생성, 수정, 삭제처럼 책임을 나눠야 요청과 응답도 선명해집니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

엔드포인트를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 기능을 몇 개의 요청으로 나눌지
- 각 요청이 목록인지 상세인지 생성인지 수정인지
- 어떤 화면에서 그 요청을 사용하는지
- 요청과 응답에서 어떤 값이 필요한지

<PromptCodeBlock>
문서 목록 조회, 문서 상세 조회, 문서 생성에 필요한 엔드포인트를 나눠서 설계해주세요.
각 엔드포인트의 경로, HTTP 메서드, 요청 파라미터, 응답 구조를 함께 정리하고, 어떤 화면에서 어떤 엔드포인트를 호출하는지도 설명해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
관리자 사용자 관리 기능에 필요한 엔드포인트를 설계해주세요.
사용자 목록 조회, 사용자 상세 조회, 권한 변경, 계정 비활성화 기능을 각각 분리하고, 경로 이름이 일관되게 유지되도록 정리해주세요.
프론트엔드에서 목록 화면과 상세 화면이 어떤 요청을 쓰는지도 함께 적어주세요.
</PromptCodeBlock>

<PromptCodeBlock>
검색 결과 화면에 필요한 엔드포인트를 설계해주세요.
검색어, 정렬, 필터, 페이지 번호를 받을 수 있게 하고, 결과 목록과 전체 개수, 현재 페이지 정보를 응답에 포함해주세요.
프론트엔드에서 URL 쿼리와 API 요청이 자연스럽게 연결되도록 설명해주세요.
</PromptCodeBlock>

<Callout type="warning" title="엔드포인트와 기능 이름이 제각각이면 금방 복잡해집니다">
비슷한 기능인데 경로 규칙이 다르면 프론트엔드와 백엔드가 서로 다른 기준으로 움직이게 됩니다. 초기에 이름 규칙을 잡아두는 편이 훨씬 낫습니다.
</Callout>

## 구현 체크리스트

- 엔드포인트별 책임이 분명한가
- 경로와 HTTP 메서드가 일관적인가
- 어떤 화면에서 어떤 엔드포인트를 쓰는지 설명되는가
- 목록/상세/생성/수정/삭제가 뒤섞이지 않는가
- 요청과 응답 구조가 후속 문서로 이어질 만큼 명확한가

## 자주 헷갈리는 개념 비교

### 엔드포인트 vs API

- API는 통신 인터페이스 전체를 뜻합니다.
- 엔드포인트는 그 안에 있는 개별 요청 경로입니다.

### 엔드포인트 vs 요청/응답 구조

- 엔드포인트는 어디로 요청하는지에 가깝습니다.
- 요청/응답 구조는 그 요청에서 어떤 데이터를 주고받는지에 가깝습니다.

### 엔드포인트 vs 라우팅

- 엔드포인트는 서버 API 경로입니다.
- 라우팅은 프론트엔드 페이지 경로입니다.
