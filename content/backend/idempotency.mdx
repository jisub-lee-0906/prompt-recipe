# 멱등성

> 한 줄 정의: 멱등성은 같은 요청이 여러 번 들어와도 최종 결과가 한 번만 처리된 것처럼 유지되는 성질입니다.

## 왜 중요한가

사용자는 새로고침을 하거나 버튼을 여러 번 누를 수 있고, 네트워크 문제로 같은 요청이 재시도될 수도 있습니다. 이때 멱등성이 없으면 중복 결제, 중복 주문, 중복 발행 같은 심각한 문제가 생깁니다. AI IDE에게 "중복 처리 막아줘"라고만 말하면 UI 비활성화 정도로 끝날 수 있어서 서버 기준의 안전 장치를 명확히 요청해야 합니다.

## 언제 쓰는가

- 결제, 주문 생성, 쿠폰 발급, 문서 발행처럼 중복 실행이 치명적인 작업일 때
- 네트워크 재시도나 큐 재처리가 발생할 수 있는 시스템일 때
- 외부 결제사, 웹훅, 모바일 앱 재전송처럼 같은 요청이 다시 올 수 있을 때

## 언제 쓰지 말아야 하는가

- 모든 요청에 같은 방식으로 억지 적용해 복잡도만 높일 때
- 읽기 요청과 변경 요청을 구분하지 않고 막연히 멱등 키를 붙일 때
- 중복 허용이 필요한 이벤트성 처리까지 무조건 한 번만 막으려 할 때

<Callout type="tip" title="클릭 막기보다 서버 멱등성이 먼저입니다">
버튼 중복 클릭 방지는 UX 보조 수단이고, 진짜 보호는 서버가 같은 요청을 한 번만 인정하는 구조에 있습니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

멱등성을 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 요청이 중복되면 위험한지
- 같은 요청을 식별하는 기준이 무엇인지
- 중복 요청 시 같은 응답을 반환할지, 오류를 줄지
- 멱등 키를 얼마나 오래 보관할지

<PromptCodeBlock>
결제 생성 API에 멱등성을 넣어주세요.
같은 사용자가 같은 결제 요청을 네트워크 문제로 여러 번 보내도 주문과 결제가 한 번만 생성되어야 합니다.
멱등 키 저장 방식과 중복 요청 시 반환할 응답도 같이 설계해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
문서 발행 API는 사용자가 버튼을 연속 클릭하거나 브라우저를 새로고침해도
같은 문서가 중복 발행되지 않게 멱등하게 처리해주세요.
발행 성공 이후 같은 요청이 다시 오면 기존 성공 결과를 반환하는 방향으로 설계해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
외부 웹훅 수신 처리에 멱등성을 적용해주세요.
같은 이벤트 id가 다시 들어오면 이미 처리된 이벤트로 판단하고,
중복 저장이나 중복 알림 발송 없이 안전하게 무시하거나 동일 결과를 반환해주세요.
</PromptCodeBlock>

<Callout type="warning" title="멱등성은 재시도 전략과 같이 설계해야 합니다">
재시도가 생기는 시스템인데 멱등성이 없으면 중복 부작용이 커집니다. 반대로 멱등성 기준이 없는데 재시도만 늘리면 문제를 키울 수 있습니다.
</Callout>

## 구현 체크리스트

- 중복되면 위험한 요청이 식별되어 있는가
- 같은 요청을 판단할 키 기준이 있는가
- 중복 요청 시 응답 정책이 정해져 있는가
- 멱등 키 저장 기간과 정리 방식이 있는가
- 외부 연동과 재시도 흐름까지 함께 고려했는가

## 자주 헷갈리는 개념 비교

### 멱등성 vs 중복 클릭 방지

- 중복 클릭 방지는 화면 UX 차원의 보조 장치입니다.
- 멱등성은 서버가 중복 실행을 막는 안정성 속성입니다.

### 멱등성 vs 재시도

- 재시도는 실패 후 다시 요청하는 전략입니다.
- 멱등성은 그 재시도가 있어도 결과가 안전하게 유지되게 합니다.

### 멱등성 vs 트랜잭션

- 트랜잭션은 한 작업 묶음의 일관성을 보장합니다.
- 멱등성은 같은 작업이 여러 번 들어와도 결과가 한 번처럼 유지되게 합니다.
