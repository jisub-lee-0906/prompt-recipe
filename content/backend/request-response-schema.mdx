# 요청/응답 구조

> 한 줄 정의: 요청/응답 구조는 API가 어떤 값을 받고 어떤 형태로 돌려주는지를 정리한 데이터 계약입니다.

## 왜 중요한가

프론트엔드는 응답 구조를 알아야 화면을 정확히 렌더링할 수 있습니다. 기획자가 "결과 붙여주세요"라고만 하면 구현자는 어떤 필드가 있는지 추측하게 됩니다. 요청/응답 구조를 명시하면 화면, API, 검증 기준이 같은 그림을 보게 됩니다.

## 언제 쓰는가

- 목록 조회, 상세 조회, 생성, 수정 API의 입력과 출력을 정의할 때
- 프론트엔드와 백엔드가 같은 필드 이름을 써야 할 때
- 에러 응답과 성공 응답의 모양을 구분해야 할 때

## 언제 쓰지 말아야 하는가

- 사실상 모든 API 설계에서 필요한 기본 요소라 생략하지 않는 편이 낫습니다

<Callout type="tip" title="요청/응답 구조를 먼저 정하면 구현 충돌이 줄어듭니다">
필드 이름, 배열 구조, 중첩 구조를 미리 맞추면 나중에 프론트엔드와 백엔드가 서로 다른 형태를 가정하는 일을 크게 줄일 수 있습니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

요청/응답 구조를 요청할 때는 아래를 같이 말해야 합니다.

- 요청에서 어떤 필드가 필요한지
- 응답이 배열인지 객체인지
- 성공과 실패 응답을 구분할지
- 프론트엔드가 반드시 써야 하는 필드가 무엇인지

<PromptCodeBlock>
문서 목록 API의 요청/응답 구조를 정의해주세요.
요청은 페이지, 정렬, 검색어를 받고, 응답은 items 배열과 totalCount, currentPage를 포함하게 해주세요.
각 item에는 id, title, description, tags, updatedAt을 넣어주세요.
</PromptCodeBlock>

<PromptCodeBlock>
문서 생성 API의 요청/응답 구조를 정의해주세요.
요청에는 title, description, category, tags를 받고, 성공 응답에는 생성된 id와 createdAt을 포함해주세요.
유효성 오류가 있으면 어떤 필드가 문제인지 알려주는 에러 구조도 함께 설계해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
사용자 상세 조회 API의 응답 구조를 정리해주세요.
기본 사용자 정보와 권한 정보, 마지막 로그인 시간, 상태 배지를 표시할 수 있는 필드를 포함해주세요.
관리자 화면에서 바로 렌더링할 수 있게 필드 이름이 직관적이도록 만들어주세요.
</PromptCodeBlock>

<Callout type="warning" title="목록과 상세 응답을 억지로 같은 모양으로 맞출 필요는 없습니다">
목적이 다르면 구조도 달라질 수 있습니다. 목록은 요약 정보 중심, 상세는 전체 정보 중심으로 나누는 편이 오히려 프론트엔드 구현에 유리합니다.
</Callout>

## 구현 체크리스트

- 요청 필드와 응답 필드가 명확히 구분되는가
- 필드 이름이 일관적인가
- 목록과 상세 구조가 목적에 맞게 나뉘는가
- 성공과 실패 응답 구조가 정의되어 있는가
- 프론트엔드가 바로 쓸 수 있을 정도로 구체적인가

## 자주 헷갈리는 개념 비교

### 요청/응답 구조 vs 엔드포인트

- 요청/응답 구조는 어떤 데이터를 주고받는지에 집중합니다.
- 엔드포인트는 그 요청을 어디로 보내는지에 집중합니다.

### 요청/응답 구조 vs API 에러 응답

- 요청/응답 구조는 성공과 일반 구조 전체를 다룹니다.
- API 에러 응답은 실패 시 반환 형식에 집중합니다.

### 요청/응답 구조 vs 폼 검증

- 요청/응답 구조는 서버 계약입니다.
- 폼 검증은 그 계약에 맞춰 프론트에서 입력을 검사하는 과정입니다.
