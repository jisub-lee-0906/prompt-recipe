# 권한 정책

> 한 줄 정의: 권한 정책은 어떤 사용자가 어떤 조건에서 어떤 기능과 데이터에 접근할 수 있는지 정하는 규칙입니다.

## 왜 중요한가

로그인만 되어 있다고 모든 기능을 사용할 수 있으면 관리자 기능 노출, 데이터 오남용, 잘못된 화면 노출이 쉽게 발생합니다. AI IDE에게 "권한 처리 넣어줘"라고만 말하면 프론트 가리기 수준으로 끝나기 쉬워서 역할, 상태, 예외 규칙을 함께 정의해야 합니다.

## 언제 쓰는가

- 관리자, 에디터, 일반 사용자처럼 역할이 나뉘는 서비스일 때
- 같은 로그인 사용자라도 소속, 플랜, 상태에 따라 기능 접근이 달라질 때
- 읽기, 수정, 삭제, 승인 같은 행위별 권한이 달라질 때

## 언제 쓰지 말아야 하는가

- 역할 이름만 만들고 실제 정책은 코드에 흩어져 있을 때
- 프론트엔드 숨김만으로 권한 처리를 끝내려 할 때
- 예외 규칙이 많은데 문서화하지 않아 팀이 다르게 해석할 때

<Callout type="tip" title="권한 정책은 화면보다 행위 중심으로 정의해야 합니다">
페이지 접근 가능 여부만이 아니라 조회, 생성, 수정, 삭제, 승인 같은 행동 단위로 규칙을 잡아야 실제 구현이 안정됩니다.
</Callout>

## 비개발자가 자주 하는 모호한 요청

<PromptCard
  badPrompt="관리자만 볼 수 있게 해주세요."
  goodPrompt="관리자, 운영자, 일반 사용자 역할을 기준으로 각 기능의 조회, 수정, 삭제, 승인 권한을 표로 정리하고 그 규칙대로 API와 화면 접근을 나눠주세요. 권한이 없을 때는 숨김 처리만 하지 말고 서버에서도 차단해주세요."
/>

## 더 좋은 요청으로 바꾸는 방법

권한 정책을 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 역할이나 사용자 상태가 있는지
- 어떤 리소스와 어떤 행동을 제어할지
- 예외 조건이 있는지
- 권한이 없을 때 화면과 API가 각각 어떻게 반응해야 하는지

<PromptCodeBlock>
문서 관리 기능의 권한 정책을 정의해주세요.
관리자, 에디터, 일반 사용자 역할이 있고,
문서 조회, 작성, 수정, 삭제, 발행 승인 권한을 역할별로 나눠주세요.
프론트엔드 표시 제어와 API 차단 기준을 같이 제안해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
프로젝트 멤버 관리 화면은 소유자만 멤버를 초대하거나 제거할 수 있게 해주세요.
일반 멤버는 목록 조회만 가능하고,
권한이 없을 때는 버튼 숨김뿐 아니라 API에서도 403 응답을 주게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
유료 플랜 사용자만 고급 검색 기능을 사용할 수 있게 정책을 설계해주세요.
역할뿐 아니라 구독 상태도 같이 확인하고,
만료 상태에서는 접근 차단과 업그레이드 유도 메시지를 보여주는 흐름까지 정리해주세요.
</PromptCodeBlock>

<Callout type="warning" title="권한 정책은 프론트 숨김으로 끝나지 않습니다">
버튼을 감추는 것은 사용자 경험용 보조 장치일 뿐이고, 실제 보호는 서버와 API에서 이뤄져야 합니다.
</Callout>

## 구현 체크리스트

- 역할과 상태가 명확히 정의되어 있는가
- 리소스와 행위 단위 권한이 정리되어 있는가
- 프론트엔드와 서버 기준이 일치하는가
- 권한 없음 응답과 화면 처리 방식이 정의되어 있는가
- 예외 규칙이 문서화되어 있는가

## 자주 헷갈리는 개념 비교

### 권한 정책 vs 인증 흐름

- 인증 흐름은 사용자가 누구인지 확인하는 과정입니다.
- 권한 정책은 확인된 사용자가 무엇을 할 수 있는지 정하는 규칙입니다.

### 권한 정책 vs RBAC

- 권한 정책은 더 넓은 개념입니다.
- RBAC는 역할 기반으로 권한을 나누는 대표적인 방식입니다.

### 권한 정책 vs 기능 플래그

- 권한 정책은 사용자 자격에 따라 접근을 나눕니다.
- 기능 플래그는 출시 범위나 실험 조건에 따라 기능 노출을 조절합니다.
