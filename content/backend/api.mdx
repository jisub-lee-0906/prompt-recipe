# API

> 한 줄 정의: API는 프론트엔드와 백엔드가 어떤 입력을 주고 어떤 결과를 돌려받을지 정한 약속입니다.

## 왜 중요한가

AI IDE에게 "API 연결해줘"라고만 요청하면, 단순 fetch 함수 정도로 끝날 수 있습니다. 하지만 실무에서 API는 경로, 메서드, 파라미터, 응답 구조, 에러 처리까지 포함하는 계약입니다.

즉, "API"를 설명할 때는 화면 요구사항만이 아니라 데이터 인터페이스까지 함께 전달해야 합니다.

## 언제 쓰는가

- 문서 검색 결과 조회
- 사용자 정보 불러오기
- 즐겨찾기 저장
- 로그인 요청
- 파일 업로드

## 언제 쓰지 말아야 하는가

- 경로만 있고 응답 형식이 없을 때
- 성공 케이스만 있고 실패 케이스가 없을 때
- 프론트엔드가 어떤 필드를 기대하는지 불분명할 때

<Callout type="warning" title="API는 경로보다 계약이 더 중요합니다">
엔드포인트 주소만 정하고 요청값과 응답 구조를 모호하게 두면 프론트엔드와 백엔드 구현이 쉽게 어긋납니다.
</Callout>

## 비개발자가 자주 하는 모호한 요청

- "검색 API 하나 붙여줘."
- "문서 저장하는 API 연결해줘."
- "백엔드랑 연동되게 해줘."

이 요청은 보통 "무엇을 보내고 무엇을 받는지"가 빠져 있습니다.

## 더 좋은 요청으로 바꾸는 방법

좋은 요청은 아래 요소를 포함합니다.

- 요청 경로와 메서드
- 필요한 파라미터
- 성공 시 응답 구조
- 실패 시 에러 메시지 처리
- 인증이나 권한이 필요한지
- 빈 결과와 중복 요청을 어떻게 다룰지

## 복붙 가능한 프롬프트

### 1. 검색 API 연결

<PromptCodeBlock>
문서 검색 API를 호출하는 함수를 만들어주세요.
검색어 문자열을 받아 /api/search?q= 형식으로 요청하고, 성공 시 문서 제목과 설명 배열을 반환하게 해주세요.
실패하면 사용자에게 보여줄 수 있는 오류 메시지도 함께 다뤄주세요.
응답이 비어 있을 때는 빈 결과 상태를 구분할 수 있는 구조도 고려해주세요.
</PromptCodeBlock>

### 2. 저장 API 설계

<PromptCodeBlock>
문서 즐겨찾기 저장 API를 설계해주세요.
POST /api/favorites 형식으로 요청하고, body에는 documentId를 포함해주세요.
성공 시 저장된 즐겨찾기 id와 상태를 반환하고, 이미 저장된 문서라면 중복 저장이 되지 않도록 처리해주세요.
</PromptCodeBlock>

<Callout type="tip" title="프론트엔드 언어를 API 언어로 번역해 전달하세요">
"문서를 찾고 싶다"는 말은 API 관점에서는 검색어 파라미터, 결과 배열, 빈 결과 처리 규칙으로 바뀌어야 합니다.
</Callout>

<Callout type="info" title="좋은 API 요청은 성공 응답보다 실패 응답이 더 또렷합니다">
성공 케이스는 비교적 쉽게 맞춰집니다. 실제 품질 차이는 권한 부족, 빈 결과, 중복 요청, 유효성 오류를 어떻게 나누는지에서 납니다.
</Callout>

## 구현 체크리스트

- 메서드와 경로가 명확한가
- 요청에 필요한 값이 빠짐없이 정의되었는가
- 응답 구조가 프론트엔드 요구와 맞는가
- 실패 시 사용자에게 어떤 메시지를 보여줄지 정리되었는가
- 중복 요청, 빈 결과, 권한 오류 같은 예외가 고려되었는가

## 자주 헷갈리는 개념 비교

### API vs 엔드포인트

- API: 전체 인터페이스 계약
- 엔드포인트: 그 계약 안의 개별 경로

### API vs 함수 호출

- 함수 호출은 코드 내부 동작
- API 호출은 시스템 간 통신

### API 성공 vs 사용자 경험 성공

- 응답이 200이어도 화면에서 필요한 필드가 없으면 UX는 실패일 수 있습니다.

### API vs 데이터 모델

- API: 주고받는 방식과 계약
- 데이터 모델: 그 계약 안에서 어떤 필드 구조를 가지는지에 대한 설계
