# 필터링 API

> 한 줄 정의: 필터링 API는 카테고리, 상태, 태그 같은 조건으로 결과 집합을 좁혀 조회할 수 있게 하는 API입니다.

## 왜 중요한가

필터 UI가 있어도 서버가 그 조건을 이해하지 못하면 실제 목록은 바뀌지 않습니다. 어떤 파라미터를 받을지, 여러 필터가 동시에 들어오면 어떻게 처리할지, 응답에 총 개수가 포함되는지까지 같이 정해야 합니다. AI IDE에게 "필터도 되게 해줘"보다 필터링 API라고 명시하는 편이 훨씬 정확합니다.

## 언제 쓰는가

- 목록 화면에서 카테고리, 태그, 상태, 가격대 같은 조건으로 결과를 좁혀야 할 때
- 검색과 함께 추가 조건을 걸어야 할 때
- 관리자 화면에서 여러 상태를 조합해 조회해야 할 때

## 언제 쓰지 말아야 하는가

- 결과 수가 매우 적어서 클라이언트에서만 필터링해도 충분할 때
- 필터 조건이 사실상 하나뿐이라 별도 구조가 과한 경우

<Callout type="tip" title="필터링 API는 필터 UI와 함께 설계해야 합니다">
프론트가 어떤 조건을 동시에 걸 수 있는지 알아야 서버 파라미터도 정할 수 있습니다. UI와 API가 따로 움직이면 금방 불일치가 생깁니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

필터링 API를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 필터 조건이 있는지
- 여러 필터를 동시에 지원할지
- 검색·정렬·페이지네이션과 함께 쓸지
- 응답에 총 개수와 현재 필터 상태가 필요한지

<PromptCodeBlock>
문서 목록 API에서 카테고리, 태그, 난이도 필터를 받을 수 있게 설계해주세요.
여러 조건이 동시에 들어와도 동작해야 하고, 현재 필터가 반영된 총 결과 수를 응답에 포함해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
상품 목록 API에 브랜드, 가격대, 재고 여부 필터를 추가해주세요.
사용자가 여러 필터를 동시에 선택할 수 있고, 필터 변경 후에도 페이지네이션과 정렬이 함께 동작하게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
관리자 사용자 목록 API에 역할, 상태, 가입일 범위 필터를 넣어주세요.
필터가 없으면 전체 결과를 주고, 잘못된 필터 값이 들어오면 에러 응답으로 구분할 수 있게 해주세요.
</PromptCodeBlock>

<Callout type="warning" title="필터 파라미터 이름이 제각각이면 프론트엔드가 금방 복잡해집니다">
카테고리, 태그, 상태처럼 자주 쓰는 조건일수록 이름 규칙을 일관되게 정해야 합니다. 그래야 UI와 API 문서가 함께 유지됩니다.
</Callout>

## 구현 체크리스트

- 필터 파라미터 이름이 명확한가
- 여러 조건 동시 적용이 가능한가
- 검색, 정렬, 페이지네이션과 함께 써도 구조가 유지되는가
- 총 결과 수와 메타 정보가 있는가
- 잘못된 필터 값 처리 기준이 있는가

## 자주 헷갈리는 개념 비교

### 필터링 API vs 검색 API

- 필터링 API는 정해진 조건으로 범위를 줄입니다.
- 검색 API는 키워드 기반 탐색이 중심입니다.

### 필터링 API vs 정렬 API

- 필터링 API는 어떤 결과를 남길지 정합니다.
- 정렬 API는 남은 결과를 어떤 순서로 보여줄지 정합니다.

### 필터링 API vs 필터 바

- 필터링 API는 서버 인터페이스입니다.
- 필터 바는 사용자가 조건을 선택하는 UI입니다.
