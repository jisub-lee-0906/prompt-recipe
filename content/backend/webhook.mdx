# 웹훅

> 한 줄 정의: 웹훅은 서비스 안에서 특정 이벤트가 발생했을 때 외부 시스템으로 HTTP 요청을 보내 알려주는 방식입니다.

## 왜 중요한가

결제 완료, 회원가입, 문서 발행 같은 이벤트를 다른 서비스와 연결하려면 서버가 먼저 알려줄 수 있어야 합니다. AI IDE에게 "이벤트 나가게 해줘"라고 하는 것보다 웹훅이라고 명시해야 어떤 시점에, 어떤 페이로드로, 어떤 재시도 규칙으로 보낼지까지 설계됩니다.

## 언제 쓰는가

- 결제 완료 후 외부 CRM이나 알림 시스템에 전달할 때
- 문서 발행, 사용자 생성 같은 이벤트를 다른 서비스와 연동할 때
- 내부 시스템과 외부 도구를 비동기로 연결하고 싶을 때

## 언제 쓰지 말아야 하는가

- 외부 서비스가 이벤트를 실시간으로 받을 필요가 없을 때
- 단순 조회형 연동인데 굳이 서버가 먼저 밀어줄 필요가 없을 때
- 실패 처리와 재시도 규칙 없이 단발 전송만 기대할 때

<Callout type="tip" title="웹훅은 성공보다 실패 처리 규칙이 더 중요할 때가 많습니다">
외부 서비스는 언제든 느리거나 실패할 수 있습니다. 재시도와 로그, 서명 검증까지 함께 설계해야 실무에서 버틸 수 있습니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

웹훅을 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 이벤트에서 발송할지
- 어떤 URL과 페이로드를 사용할지
- 재시도와 실패 로그가 필요한지
- 보안 검증 방식이 필요한지

<PromptCodeBlock>
결제 완료 이벤트가 발생하면 외부 정산 서비스로 웹훅을 보내주세요.
어떤 URL로 보낼지, 어떤 JSON 페이로드를 담을지, 실패하면 몇 번 재시도할지, 서명 검증은 어떻게 할지도 함께 설계해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
문서 발행 시 외부 검색 인덱싱 서비스로 웹훅을 보내주세요.
payload에는 문서 id, slug, title, category, publishedAt을 넣고, 실패 시에는 재시도 큐에 넣어 나중에 다시 보낼 수 있게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
사용자 가입 완료 후 CRM 시스템으로 웹훅을 전송해주세요.
개인정보는 필요한 최소 필드만 보내고, 외부 서비스 응답 실패 시 내부 로그를 남기고 재시도할 수 있게 해주세요.
</PromptCodeBlock>

<Callout type="warning" title="웹훅은 보내는 것보다 추적이 더 중요할 수 있습니다">
외부 시스템 장애는 자주 생깁니다. 발송 기록, 실패 로그, 재시도 상태가 없으면 운영 단계에서 원인 파악이 매우 어려워집니다.
</Callout>

## 구현 체크리스트

- 발송 트리거 이벤트가 명확한가
- 요청 페이로드가 정의되어 있는가
- 재시도 규칙이 있는가
- 보안 검증이나 서명 방식이 있는가
- 실패 로그와 추적 경로가 있는가

## 자주 헷갈리는 개념 비교

### 웹훅 vs API 호출

- 웹훅은 서버가 먼저 외부로 보내는 방식입니다.
- 일반 API 호출은 클라이언트나 다른 서비스가 요청을 시작합니다.

### 웹훅 vs 큐

- 웹훅은 외부 알림 전달 방식입니다.
- 큐는 그 전달을 안정적으로 처리하는 내부 비동기 구조일 수 있습니다.

### 웹훅 vs 이벤트 트래킹

- 웹훅은 외부 시스템 연동 목적입니다.
- 이벤트 트래킹은 분석 목적 데이터 수집에 더 가깝습니다.
