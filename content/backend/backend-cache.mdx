# 백엔드 캐시

> 한 줄 정의: 백엔드 캐시는 자주 반복되는 요청 결과를 서버 쪽에 저장해 응답 속도와 시스템 부하를 줄이는 전략입니다.

## 왜 중요한가

문서 목록, 인기 문서, 검색 결과처럼 자주 요청되는 데이터를 매번 원본에서 계산하면 비용이 커집니다. 백엔드 캐시는 이런 부담을 줄이는 핵심 전략입니다. AI IDE에게 "응답 빠르게 해줘"보다 캐시 전략을 같이 요청해야 어디를, 얼마나, 어떤 기준으로 저장할지 명확해집니다.

## 언제 쓰는가

- 같은 결과가 짧은 시간 안에 반복 요청될 때
- 계산 비용이 큰 결과를 여러 사용자가 함께 볼 때
- 검색 결과나 목록 API의 부하를 줄이고 싶을 때

## 언제 쓰지 말아야 하는가

- 항상 최신값이 꼭 필요한 민감한 데이터일 때
- 캐시 무효화 규칙 없이 임의로 저장해 오래된 데이터를 오래 노출할 때
- 사용자별 개인화 데이터가 많아 공유 캐시 이점이 낮을 때

<Callout type="tip" title="캐시는 저장보다 무효화 기준이 더 중요합니다">
무엇을 얼마나 오래 저장할지와, 언제 다시 계산할지를 같이 정해야 실제로 안전하게 쓸 수 있습니다.
</Callout>

## 비개발자가 자주 하는 모호한 요청

## 더 좋은 요청으로 바꾸는 방법

백엔드 캐시를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 응답을 캐시할지
- 얼마나 오래 유지할지
- 언제 무효화할지
- 개인화 데이터와 공용 데이터를 어떻게 나눌지

<PromptCodeBlock>
문서 목록 API는 백엔드 캐시를 적용해주세요.
자주 바뀌지 않는 목록 결과는 짧은 시간 동안 캐시하고, 문서가 수정되면 관련 캐시는 적절히 무효화되게 해주세요.
검색 결과와 최신 문서 목록은 서로 다른 캐시 전략을 쓸 수 있게 구분해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
인기 문서 위젯 API를 캐시해주세요.
여러 사용자가 같은 데이터를 보므로 공용 캐시가 가능하고, 너무 자주 다시 계산하지 않도록 TTL을 두되 새 통계가 반영될 수 있게 적절한 갱신 주기도 정해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
검색 API는 동일한 검색어와 필터 조합에 대해 짧은 시간 캐시를 사용해주세요.
다만 문서가 새로 발행되면 관련 검색 결과가 오래 남지 않게 무효화 전략도 함께 설계해주세요.
</PromptCodeBlock>

<Callout type="warning" title="캐시된 결과가 오래된 상태로 남으면 신뢰가 빠르게 떨어집니다">
응답 속도는 빨라져도 내용이 틀리면 사용자 신뢰가 더 크게 깨집니다. 무효화와 최신성 기준이 반드시 필요합니다.
</Callout>

## 구현 체크리스트

- 캐시 대상 응답이 분명한가
- TTL이나 무효화 기준이 있는가
- 개인화 데이터와 공용 데이터가 구분되는가
- 검색, 목록, 상세가 각각 다른 전략을 가질 수 있는가
- 오래된 데이터 노출 위험을 통제하는가

## 자주 헷갈리는 개념 비교

### 백엔드 캐시 vs 프론트엔드 캐시

- 백엔드 캐시는 서버 응답 자체를 빠르게 만듭니다.
- 프론트엔드 캐시는 브라우저 쪽 재사용 전략입니다.

### 백엔드 캐시 vs SSG

- 백엔드 캐시는 요청 시점 처리 성능 전략입니다.
- SSG는 빌드 시점에 페이지를 미리 생성하는 전략입니다.

### 백엔드 캐시 vs 레이트 리밋

- 백엔드 캐시는 성능 최적화 목적입니다.
- 레이트 리밋은 남용 방지 목적입니다.
