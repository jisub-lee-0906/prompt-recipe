# 검색 인덱스

> 한 줄 정의: 검색 인덱스는 검색어와 문서를 빠르게 연결하기 위해 원본 데이터와 별도로 정리한 검색용 구조입니다.

## 왜 중요한가

데이터가 많아질수록 원본 테이블이나 원본 문서만 직접 뒤져서는 검색 속도와 정확도를 맞추기 어렵습니다. AI IDE에게 "검색 빠르게 해줘"라고만 말하면 단순 필터 수준으로 끝날 수 있어서 어떤 필드를 색인할지, 언제 갱신할지, 어떤 검색 경험을 목표로 하는지까지 같이 지시해야 합니다.

## 언제 쓰는가

- 검색 대상이 많아져 단순 문자열 포함 검색으로는 느려질 때
- 제목, 설명, 태그, 본문 일부처럼 여러 필드를 함께 검색해야 할 때
- 정렬, 추천, 자동완성, 하이라이트 같은 검색 품질을 높이고 싶을 때

## 언제 쓰지 말아야 하는가

- 데이터가 아주 적어 단순 필터만으로도 충분할 때
- 색인 갱신 전략 없이 일단 저장만 하려 할 때
- 검색 정확도보다 구현 단순성이 더 중요한 초기 프로토타입일 때

<Callout type="tip" title="인덱스는 복사본이 아니라 검색용 뷰입니다">
원본 데이터를 그대로 복제하는 것이 아니라 검색에 필요한 필드와 형태로 재구성하는 것이 핵심입니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

검색 인덱스를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 데이터를 검색 대상으로 삼는지
- 어떤 필드를 색인할지
- 갱신 시점이 실시간인지 배치인지
- 검색 결과 정렬 기준이 무엇인지

<PromptCodeBlock>
문서 검색용 인덱스를 설계해주세요.
제목, 설명, 태그, 본문 일부를 검색 대상으로 삼고,
문서 수정 시 인덱스가 같이 갱신되게 해주세요.
정확도 높은 결과가 먼저 보이도록 정렬 기준도 제안해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
상품 검색 인덱스를 설계해주세요.
상품명, 브랜드, 카테고리, 태그를 색인하고,
품절 상품은 검색은 되되 기본 정렬에서 뒤로 밀리게 해주세요.
자동완성과 필터 확장 가능성도 고려해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
관리자 검색은 운영 로그를 빠르게 찾는 것이 목적입니다.
메시지 본문뿐 아니라 레벨, 서비스명, 요청 id, 시간 범위를 기준으로 검색 가능한 인덱스 구조를 제안해주세요.
오래된 데이터는 별도 보관 정책도 같이 고려해주세요.
</PromptCodeBlock>

<Callout type="warning" title="인덱스가 늦게 갱신되면 검색 신뢰도가 떨어집니다">
검색 성능만 보지 말고 원본 데이터와 색인 데이터가 얼마나 빨리 일치해야 하는지도 함께 설계해야 합니다.
</Callout>

## 구현 체크리스트

- 검색 대상 필드가 정의되어 있는가
- 색인 갱신 시점이 정리되어 있는가
- 정렬 기준과 우선순위가 있는가
- 오래된 색인 데이터 정리 전략이 있는가
- 검색 정확도와 성능 목표가 균형 있게 잡혀 있는가

## 자주 헷갈리는 개념 비교

### 검색 인덱스 vs 검색 API

- 검색 인덱스는 내부 데이터 구조입니다.
- 검색 API는 그 구조를 이용해 결과를 반환하는 인터페이스입니다.

### 검색 인덱스 vs 데이터베이스 인덱스

- 검색 인덱스는 검색 품질과 기능을 위해 별도 설계한 구조일 수 있습니다.
- 데이터베이스 인덱스는 일반 쿼리 성능을 높이는 저장소 레벨 최적화입니다.

### 검색 인덱스 vs 필터링 API

- 검색 인덱스는 텍스트 검색과 관련도 계산에 가깝습니다.
- 필터링 API는 명확한 조건으로 대상을 좁히는 데 가깝습니다.
