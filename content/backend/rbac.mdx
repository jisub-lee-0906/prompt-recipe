# RBAC

> 한 줄 정의: RBAC는 사용자 역할에 따라 접근 가능한 기능과 행동을 나누는 역할 기반 권한 제어 방식입니다.

## 왜 중요한가

권한이 복잡해질수록 사용자마다 개별 규칙을 코드에 박아 넣는 방식은 빠르게 관리 불가능해집니다. AI IDE에게 "관리자만 가능하게 해줘"라고만 말하면 화면 숨김 수준으로 끝날 수 있어서 역할 정의, 행위 단위 권한, 예외 조건을 함께 정리해야 합니다.

## 언제 쓰는가

- 관리자, 운영자, 에디터, 일반 사용자처럼 역할이 분리된 서비스일 때
- 문서 승인, 멤버 초대, 결제 관리처럼 행위별 권한이 달라질 때
- 여러 화면과 API에서 같은 권한 규칙을 재사용해야 할 때

## 언제 쓰지 말아야 하는가

- 사용자 속성, 소속, 구독 상태 같은 조건이 더 중요해 역할만으로 설명이 어려울 때
- 역할 이름은 있지만 실제 권한 정의가 제각각일 때
- 예외 규칙이 너무 많은데 역할 구조를 계속 늘려만 갈 때

<Callout type="tip" title="역할보다 행동 매핑표가 더 중요합니다">
RBAC는 '누가 누구인지'보다 '그 역할이 무엇을 할 수 있는지'를 표처럼 명확히 적어야 실제 구현과 테스트가 쉬워집니다.
</Callout>

## 비개발자가 자주 하는 모호한 요청

## 더 좋은 요청으로 바꾸는 방법

RBAC를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 역할이 있는지
- 각 역할이 어떤 행동을 할 수 있는지
- 역할만으로 부족한 예외 조건이 있는지
- UI 숨김과 서버 차단을 어떻게 나눌지

<PromptCodeBlock>
문서 협업 서비스의 RBAC를 설계해주세요.
관리자, 에디터, 리뷰어, 일반 사용자 역할이 있고,
문서 조회, 작성, 수정, 삭제, 승인, 발행 권한을 권한 그룹별로 정리해주세요.
프론트엔드 표시 제어와 API 권한 검사 기준도 같이 제안해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
프로젝트 관리 도구에서 소유자만 멤버 초대와 권한 변경을 할 수 있게 RBAC를 정리해주세요.
일반 멤버는 조회와 댓글만 가능하고,
권한이 없을 때는 버튼 숨김과 403 응답 기준을 같이 설계해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
운영자 대시보드 RBAC를 정리해주세요.
고객 문의 조회, 환불 승인, 통계 조회, 시스템 설정 변경 권한을 권한 그룹별로 나누고,
감사 로그에 어떤 권한 변경을 남겨야 하는지도 포함해주세요.
</PromptCodeBlock>

<Callout type="warning" title="RBAC만으로 모든 예외를 처리하려 하면 역할이 폭증합니다">
소속 조직, 구독 상태, 리소스 소유 여부까지 중요하면 역할 외 조건을 함께 쓰는 구조를 고려해야 합니다.
</Callout>

## 구현 체크리스트

- 역할 목록이 명확한가
- 권한 그룹별 행동 권한 표가 있는가
- 프론트와 서버 기준이 일치하는가
- 403 응답과 UX 처리가 정의되어 있는가
- 권한 변경 로그가 필요한지 정리되어 있는가

## 자주 헷갈리는 개념 비교

### RBAC vs 권한 정책

- 권한 정책은 더 넓은 개념입니다.
- RBAC는 그중 역할 기반 방식입니다.

### RBAC vs 인증 흐름

- 인증 흐름은 사용자가 누구인지 확인합니다.
- RBAC는 확인된 사용자가 무엇을 할 수 있는지 정합니다.

### RBAC vs 기능 플래그

- RBAC는 사용자 자격 기반 제어입니다.
- 기능 플래그는 출시 범위나 실험 제어에 가깝습니다.
