# 검색 API

> 한 줄 정의: 검색 API는 사용자가 입력한 검색어와 조건을 기준으로 관련 결과를 찾아 반환하는 API입니다.

## 왜 중요한가

검색 UI가 있어도 서버 응답 구조가 약하면 실제 검색 경험은 쉽게 흔들립니다. 어떤 필드를 검색하는지, 정렬은 어떻게 되는지, 결과가 없을 때 무엇을 돌려주는지까지 API 수준에서 정리돼야 합니다. AI IDE에게 "검색 기능 만들어줘"보다 "검색 API를 설계해줘"라고 요청해야 프론트와 백 모두 안정적입니다.

## 언제 쓰는가

- 문서, 상품, 사용자처럼 키워드 기반 탐색이 필요할 때
- 제목, 설명, 태그, 카테고리 등을 기준으로 결과를 찾을 때
- 검색 바와 결과 목록이 함께 동작해야 할 때

## 언제 쓰지 말아야 하는가

- 정적인 소규모 데이터에서 클라이언트 필터만으로 충분할 때
- 검색보다 단순한 카테고리 탐색만으로도 충분할 때

<Callout type="tip" title="검색 API는 검색 UI와 함께 설계해야 합니다">
프론트가 제목만 보여줄지, 설명과 태그도 함께 보여줄지에 따라 API 응답 필드도 달라집니다. 검색 결과 화면을 생각하면서 설계하는 편이 좋습니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

검색 API를 요청할 때는 아래를 같이 말해야 합니다.

- 무엇을 검색 대상으로 삼을지
- 필터나 정렬이 함께 필요한지
- 응답에 총 개수와 페이지 정보가 필요한지
- 결과 없음 상황을 어떻게 처리할지

</PromptCodeBlock>

<PromptCodeBlock>

프론트엔드가 검색 결과 페이지네이션과 `총 N개 결과` 문구를 만들 수 있어야 합니다.
</PromptCodeBlock>

<PromptCodeBlock>

필요하면 프론트엔드가 그대로 보여줄 수 있는 안내 코드나 메시지도 함께 정의해주세요.
</PromptCodeBlock>

<Callout type="warning" title="검색 API는 결과 배열만 주고 끝내면 금방 한계가 옵니다">
정렬, 필터, 총 개수, 페이지 정보가 없으면 프론트엔드에서 검색 경험을 풍부하게 만들기 어렵습니다.
</Callout>

## 구현 체크리스트

- 검색 대상 필드가 정의되어 있는가
- 필터와 정렬 구조가 함께 설계되었는가
- 결과 개수와 페이지 메타 정보가 있는가
- 너무 짧은 검색어 같은 예외가 고려되는가
- 검색 UI와 바로 연결할 수 있을 만큼 구체적인가

## 자주 헷갈리는 개념 비교

### 검색 API vs 검색 바

- 검색 API는 서버 인터페이스입니다.
- 검색 바는 검색어를 입력하는 UI입니다.

### 검색 API vs 필터링 API

- 검색 API는 키워드 기반 탐색에 초점이 있습니다.
- 필터링 API는 정해진 조건으로 범위를 줄이는 데 초점이 있습니다.

### 검색 API vs 페이지네이션 API

- 검색 API는 검색 로직이 핵심입니다.
- 페이지네이션 API는 많은 결과를 나눠 전달하는 구조가 핵심입니다.
