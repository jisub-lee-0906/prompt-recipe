# 큐

> 한 줄 정의: 큐는 오래 걸리거나 실패 가능성이 있는 작업을 즉시 응답 흐름에서 분리해 비동기로 처리하는 구조입니다.

## 왜 중요한가

이메일 발송, 웹훅 전송, 검색 인덱싱처럼 즉시 끝나지 않는 작업을 요청 흐름 안에서 모두 처리하면 응답이 느려지고 실패 처리도 복잡해집니다. AI IDE에게 "나중에 처리되게 해줘"보다 큐라고 명시하면 작업 분리, 재시도, 상태 추적까지 더 명확하게 설계할 수 있습니다.

## 언제 쓰는가

- 이메일 발송, 웹훅 전송, 인덱싱처럼 비동기 작업이 필요할 때
- 요청 응답을 빠르게 끝내고 후속 처리를 따로 돌리고 싶을 때
- 실패 시 재시도나 순차 처리가 필요한 작업에서

## 언제 쓰지 말아야 하는가

- 사용자가 즉시 결과를 받아야 하는 핵심 동작일 때
- 작업이 매우 단순하고 즉시 끝나 별도 비동기 구조가 과한 경우
- 상태 추적 없이 큐만 붙이면 오히려 운영이 더 복잡해질 때

<Callout type="tip" title="큐는 느린 작업을 숨기는 장치가 아니라 분리하는 장치입니다">
핵심은 사용자 응답과 후속 처리를 분리하는 것입니다. 작업이 큐에 들어간 뒤 어떤 상태로 흘러가는지도 같이 설계해야 합니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

큐를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 작업을 큐로 분리할지
- 사용자에게는 언제 응답을 줄지
- 실패 시 재시도와 상태 추적이 필요한지
- 작업 완료 여부를 사용자에게 보여줄 필요가 있는지

<PromptCodeBlock>
결제 완료 후 외부 웹훅 전송은 큐로 분리해주세요.
사용자에게는 결제 완료 응답을 먼저 보내고, 웹훅은 비동기로 처리하며 실패 시 재시도와 로그 추적이 가능하게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
문서 발행 후 검색 인덱싱 작업은 큐로 처리해주세요.
문서 저장 자체는 빠르게 끝나야 하고, 인덱싱은 백그라운드에서 돌며 실패하면 다시 시도할 수 있게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
대량 이메일 발송 기능은 큐 기반으로 설계해주세요.
한 번에 모든 메일을 보내지 말고 작업 단위를 나눠 순차 처리하고, 진행 상태와 실패 건수도 확인할 수 있게 해주세요.
</PromptCodeBlock>

<Callout type="warning" title="큐는 넣는 순간이 아니라 완료 추적까지 있어야 실무에서 버팁니다">
작업이 큐에 들어갔는지, 실패했는지, 몇 번 재시도했는지 모르면 운영 단계에서 원인 파악이 매우 어렵습니다.
</Callout>

## 구현 체크리스트

- 어떤 작업을 큐로 분리할지 명확한가
- 사용자 응답과 비동기 작업이 분리되는가
- 재시도와 실패 기록이 있는가
- 진행 상태 추적이 가능한가
- 즉시 처리해야 할 작업과 섞이지 않는가

## 자주 헷갈리는 개념 비교

### 큐 vs 재시도

- 큐는 비동기 작업 처리 구조입니다.
- 재시도는 실패한 작업을 다시 시도하는 전략입니다.

### 큐 vs 웹훅

- 큐는 작업을 처리하는 내부 구조입니다.
- 웹훅은 외부로 알림을 보내는 방식입니다.

### 큐 vs 스케줄러

- 큐는 작업을 순서대로 처리합니다.
- 스케줄러는 특정 시점에 작업을 시작하게 할 수 있습니다.
