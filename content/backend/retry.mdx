# 재시도

> 한 줄 정의: 재시도는 일시적인 실패 상황에서 동일한 요청이나 작업을 다시 시도해 복구하는 전략입니다.

## 왜 중요한가

네트워크 문제나 외부 서비스 장애는 항상 일어날 수 있습니다. 모든 실패를 즉시 최종 실패로 처리하면 복구 가능한 상황까지 놓치게 됩니다. AI IDE에게 "실패하면 다시 해봐"라고 하는 것보다 재시도 전략이라고 명확히 요청해야 대상, 횟수, 간격, 중단 조건까지 설계됩니다.

## 언제 쓰는가

- 외부 API 호출이나 웹훅 전송처럼 일시적 실패가 생길 수 있을 때
- 큐 기반 비동기 작업이 잠깐 실패해도 나중에 성공 가능성이 있을 때
- 네트워크 불안정이나 타임아웃이 잦은 연동 구간에서

## 언제 쓰지 말아야 하는가

- 입력값 자체가 잘못돼 절대 성공할 수 없는 요청일 때
- 같은 요청을 반복하면 더 큰 부작용이 생길 수 있을 때
- 사용자 액션을 중복 실행하면 위험한 작업인데 멱등성 보장이 없을 때

<Callout type="tip" title="재시도는 일시적 실패에만 적용해야 합니다">
모든 실패를 무조건 다시 보내는 것은 좋은 전략이 아닙니다. 네트워크 오류와 유효성 오류는 전혀 다르게 다뤄야 합니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

재시도를 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 실패에만 재시도할지
- 몇 번까지 시도할지
- 간격을 어떻게 둘지
- 최종 실패 시 어떻게 기록하거나 알릴지

<PromptCodeBlock>
외부 웹훅 전송이 네트워크 오류나 5xx로 실패하면 자동으로 재시도해주세요.
최대 몇 번까지 다시 시도할지, 간격은 어떻게 둘지, 최종 실패 시 어디에 기록할지도 함께 설계해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
검색 인덱싱 작업이 일시적으로 실패하면 재시도 큐에 넣어주세요.
잘못된 입력 때문에 실패한 경우에는 재시도하지 말고 바로 실패로 처리해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
외부 결제 승인 확인 요청은 재시도 전략을 적용해주세요.
다만 같은 승인 요청이 중복 처리되지 않도록 멱등성이나 중복 방지 기준도 같이 고려해주세요.
</PromptCodeBlock>

<Callout type="warning" title="재시도는 중복 실행 위험과 함께 봐야 합니다">
특히 결제나 삭제처럼 부작용이 큰 작업은 멱등성 없이 재시도하면 더 위험할 수 있습니다.
</Callout>

## 구현 체크리스트

- 재시도 대상 실패 유형이 정의되어 있는가
- 재시도 횟수와 간격이 정해져 있는가
- 최종 실패 기록 경로가 있는가
- 멱등성이나 중복 방지 기준이 있는가
- 재시도하면 안 되는 실패가 구분되는가

## 자주 헷갈리는 개념 비교

### 재시도 vs 레이트 리밋

- 재시도는 실패 후 다시 보내는 전략입니다.
- 레이트 리밋은 요청 수를 제한하는 보호 장치입니다.

### 재시도 vs 큐

- 재시도는 실패 후 처리 방식입니다.
- 큐는 그 작업을 비동기로 관리하는 구조일 수 있습니다.

### 재시도 vs 폴백

- 재시도는 같은 작업을 다시 시도합니다.
- 폴백은 다른 대체 경로로 넘어갑니다.
