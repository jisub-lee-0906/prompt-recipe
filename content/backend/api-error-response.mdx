# API 에러 응답

> 한 줄 정의: API 에러 응답은 실패 상황에서 프론트엔드가 이해하고 처리할 수 있게 정리한 오류 반환 형식입니다.

## 왜 중요한가

성공 응답만 정의하고 에러 응답을 비워두면 프론트엔드는 실패 상황을 일관되게 처리하기 어렵습니다. AI IDE에게 "실패하면 에러 주세요"라고 하는 것보다 어떤 필드로, 어떤 코드로, 어떤 메시지를 줄지 요청해야 실제 화면이 안정적으로 동작합니다.

## 언제 쓰는가

- 유효성 오류, 권한 부족, 리소스 없음, 서버 오류를 구분해야 할 때
- 프론트엔드가 에러 상태나 인라인 오류를 안정적으로 보여줘야 할 때
- API 문서와 예외 처리 규칙을 표준화하고 싶을 때

## 언제 쓰지 말아야 하는가

- 예외가 거의 없습니다. API가 있다면 에러 응답 규칙도 함께 있어야 합니다.

<Callout type="tip" title="에러 응답은 사람과 코드가 함께 읽을 수 있어야 합니다">
사용자용 메시지와 개발자가 처리할 수 있는 코드나 필드 이름이 함께 있어야 프론트엔드가 안정적으로 분기할 수 있습니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

API 에러 응답을 요청할 때는 아래를 같이 말해야 합니다.

- 어떤 실패 유형을 구분해야 하는지
- 프론트엔드가 무엇을 보고 분기할지
- 필드 오류가 필요한지
- 사용자에게 그대로 보여줄 메시지인지 내부 코드인지

<PromptCodeBlock>
문서 API의 에러 응답 형식을 표준화해주세요.
유효성 오류, 권한 부족, 존재하지 않는 문서, 서버 오류를 구분할 수 있게 code와 message를 포함하고, 필요하면 fieldErrors도 함께 내려주세요.
</PromptCodeBlock>

<PromptCodeBlock>
회원가입 API의 에러 응답 구조를 정리해주세요.
이메일 중복, 비밀번호 형식 오류, 인증 만료 같은 경우를 구분할 수 있어야 하고, 프론트엔드가 어떤 입력 필드에 오류를 보여줘야 하는지도 알 수 있게 해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
문서 상세 조회 API에서 slug가 잘못됐을 때의 에러 응답을 설계해주세요.
404 상황과 권한 부족 상황을 명확히 구분하고, 프론트엔드가 각각 다른 화면을 보여줄 수 있게 코드와 메시지를 함께 내려주세요.
</PromptCodeBlock>

<Callout type="warning" title="모든 실패를 같은 500 메시지로 묶으면 프론트엔드가 대응할 수 없습니다">
유효성 오류, 권한 부족, 리소스 없음은 각각 다른 UI 처리가 필요합니다. 에러 응답이 너무 단순하면 화면 쪽에서 분기할 정보가 사라집니다.
</Callout>

## 구현 체크리스트

- 실패 유형별 코드가 구분되는가
- 사용자용 메시지와 분기용 코드가 함께 있는가
- 필드 오류가 필요한 경우 구조가 있는가
- 프론트엔드가 바로 처리할 수 있을 정도로 명확한가
- 성공 응답 구조와 혼동되지 않는가

## 자주 헷갈리는 개념 비교

### API 에러 응답 vs 요청/응답 구조

- API 에러 응답은 실패 시 반환 형식에 집중합니다.
- 요청/응답 구조는 성공과 전체 계약까지 포함한 더 넓은 구조입니다.

### API 에러 응답 vs 에러 상태

- API 에러 응답은 서버가 보내는 데이터 형식입니다.
- 에러 상태는 그 데이터를 바탕으로 프론트가 보여주는 화면입니다.

### API 에러 응답 vs HTTP 상태 코드

- HTTP 상태 코드는 응답의 큰 분류입니다.
- 에러 응답 본문은 더 구체적인 실패 이유를 담습니다.
