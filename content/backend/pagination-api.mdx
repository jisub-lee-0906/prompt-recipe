# 페이지네이션 API

> 한 줄 정의: 페이지네이션 API는 많은 결과를 일정 단위로 잘라서 요청하고 응답하는 방식입니다.

## 왜 중요한가

목록이 많아질수록 한 번에 전부 내려주는 API는 비효율적입니다. 프론트엔드도 현재 페이지, 전체 개수, 다음 이동 가능 여부를 알아야 UI를 안정적으로 만들 수 있습니다. AI IDE에게 "목록 API 만들어줘"만으로는 부족하고, 페이지네이션 API라고 명시해야 필요한 필드를 함께 설계할 수 있습니다.

## 언제 쓰는가

- 검색 결과, 관리자 목록, 문서 목록처럼 결과 수가 많을 때
- 페이지 번호 기반 UI나 결과 범위 표시가 필요할 때
- 서버와 프론트 모두 응답 크기를 제어해야 할 때

## 언제 쓰지 말아야 하는가

- 결과 수가 매우 적어 한 번에 전부 내려도 무리가 없을 때
- 연속 소비 경험이 더 중요해서 무한 스크롤용 커서 기반 구조를 택할 때

<Callout type="tip" title="페이지네이션 API는 UI와 함께 설계해야 합니다">
프론트엔드에서 무엇을 보여줄지 알아야 응답 필드도 정할 수 있습니다. `items`만 주는 것보다 `totalCount`, `currentPage`, `pageSize` 같은 메타 정보를 함께 주는 편이 낫습니다.
</Callout>

## 더 좋은 요청으로 바꾸는 방법

페이지네이션 API를 요청할 때는 아래를 같이 말해야 합니다.

- 페이지 번호 기반인지 커서 기반인지
- 요청에서 어떤 파라미터를 받을지
- 응답에 어떤 메타 정보가 필요한지
- 정렬이나 검색과 함께 쓸지

<PromptCodeBlock>
문서 목록 API를 페이지네이션 구조로 설계해주세요.
요청은 page와 pageSize를 받고, 응답에는 items 배열과 totalCount, currentPage, pageSize를 포함해주세요.
프론트엔드가 페이지 번호 UI를 만들 수 있게 충분한 메타 정보를 주세요.
</PromptCodeBlock>

<PromptCodeBlock>
관리자 사용자 목록 API에 페이지네이션을 붙여주세요.
검색어와 정렬 조건도 함께 받을 수 있게 하고, 응답에는 전체 사용자 수와 현재 페이지 범위가 계산 가능하도록 필요한 필드를 포함해주세요.
</PromptCodeBlock>

<PromptCodeBlock>
검색 결과 API를 페이지네이션 방식으로 설계해주세요.
검색어, 필터, 정렬, 페이지 번호를 함께 받을 수 있게 하고, 응답은 결과 배열과 총 결과 수를 포함해주세요.
프론트엔드가 `총 240개 중 21-40개` 같은 문구를 만들 수 있게 해주세요.
</PromptCodeBlock>

<Callout type="warning" title="페이지 데이터만 주고 총 개수를 안 주면 UI가 제한됩니다">
프론트엔드가 페이지 번호, 전체 범위, 마지막 페이지 여부를 계산해야 한다면 메타 정보가 반드시 필요합니다. 최소한 무엇을 보여줄지에 맞는 응답 필드를 같이 정해야 합니다.
</Callout>

## 구현 체크리스트

- 요청 파라미터가 명확한가
- 응답에 메타 정보가 충분한가
- 검색·정렬과 함께 써도 구조가 유지되는가
- 프론트엔드 페이지네이션 UI와 잘 연결되는가
- 성능상 한 번에 너무 많은 데이터를 내리지 않는가

## 자주 헷갈리는 개념 비교

### 페이지네이션 API vs 페이지네이션 UI

- 페이지네이션 API는 서버 응답 구조입니다.
- 페이지네이션 UI는 그 구조를 바탕으로 만든 화면입니다.

### 페이지네이션 API vs 검색 API

- 페이지네이션 API는 결과를 나눠 전달하는 방식입니다.
- 검색 API는 검색어 기반 결과 조회가 핵심입니다.

### 페이지네이션 API vs 무한 스크롤

- 페이지네이션 API는 보통 페이지 번호 기반과 잘 맞습니다.
- 무한 스크롤은 커서 기반 구조가 더 잘 맞는 경우가 많습니다.
